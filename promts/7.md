ПРОМПТ: ИССЛЕДОВАНИЕ И ПЕРЕПРОЕКТИРОВАНИЕ UX/UI «ПУХЛЯША»

Проведи глубокое практическое исследование и продуктово-архитектурный аудит перед продолжением разработки «Пухляша».

Работай на русском языке. Не начинай реализацию и не меняй код. Сначала исследование → анализ → модель → рекомендации → влияние на текущую архитектуру → план следующего этапа.

## 1. КОНТЕКСТ

Текущий Telegram-бот уже имеет меню примерно такого вида:

- 🎯 Подобрать диету
- 👤 Кабинет
- 🍲 Рецепт от Пухляша
- 👨‍🍳 Рецепты
- 🧊 Холодильник
- 💰 По бюджету
- 👨‍🍳 Шеф на телефоне
- ⏰ Расписание
- 🐈 Пухляш
- ℹ️ Помощь

Проблема: часть пунктов пересекается по смыслу. «Рецепт от Пухляша», «Рецепты», «Холодильник», «По бюджету», «Пухляш» воспринимаются как отдельные функции, хотя между ними есть общие пользовательские сценарии.

Нужно определить новую информационную архитектуру продукта.

Предварительная гипотеза крупных разделов:

- 👤 Кабинет
- 🍽 Питание
- 👨‍🍳 Рецепты
- 💪 Фитнес
- 💰 Бюджет
- 🔍 Умный поиск / Помощник

Это НЕ принятое решение. Проверь его исследованием.

---

# 2. ГЛАВНАЯ ЗАДАЧА

Определи, каким должен быть UX «Пухляша», чтобы пользователь:

1. не изучал меню самостоятельно;
2. быстро понимал, что продукт умеет;
3. мог найти любую функцию обычным человеческим запросом;
4. постепенно открывал полезные возможности;
5. не получал десятки дублирующих кнопок;
6. видел персонально актуальные действия;
7. понимал практическую пользу функций, а не только их название.

Исследуй концепцию:

**«Пухляш и Ирисочка не просто персонажи, а персональный навигационный и обучающий слой продукта».**

При этом не превращай их в навязчивого чат-бота.

---

# 3. АДАПТИВНЫЙ ПОМОЩНИК

Исследуй модель помощника, который может:

- объяснить, что умеет продукт;
- провести новичка по разделу;
- подсказать следующий шаг;
- найти нужную функцию;
- открыть нужный экран;
- объяснить незнакомую возможность;
- учитывать уже использованные функции;
- не повторять навязчивые предложения;
- показывать полезные возможности в подходящий момент.

Пример:

Пользователь:

> «Где посмотреть, сколько я потратил за месяц?»

Помощник:

> «Это находится в 💰 Бюджет → 📊 Мои расходы. Открыть?»

Другой пример:

> «Что можно сделать с чеком?»

Помощник должен знать соответствующую возможность и объяснить практическую пользу.

Исследуй, нужен ли для этого отдельный **реестр возможностей продукта (Capability Registry)** и как он должен быть связан с навигацией, поиском и помощником.

---

# 4. УМНЫЙ ПОИСК

Исследуй глобальный поиск не только по названиям кнопок, а по намерениям пользователя.

Примеры:

> «Хочу посмотреть продукты на неделю»

> «Сколько мне обойдётся эта диета?»

> «У меня осталось 2500 рублей до зарплаты»

> «Хочу рецепт из того, что есть дома»

> «Где мои тренировки?»

> «Я забыл, где список покупок»

Определи минимальную архитектуру такого поиска.

Не проектируй сложный AI-агент без необходимости.

Исследуй, какие запросы можно покрыть:

- обычным поиском;
- намерениями;
- реестром возможностей;
- контекстом пользователя;
- LLM только там, где это действительно оправдано.

# 6. ЦЕНЫ ПО РОССИИ

Исследуй реальные источники цен на продукты в России.

Нужно выяснить:

1. какие официальные источники доступны;
2. что можно получить по России;
3. что можно получить по регионам;
4. что можно получить по городам;
5. какие данные доступны регулярно;
6. какие данные можно использовать легально и технически;
7. насколько средние цены подходят для расчёта питания;
8. чем отличаются статистические цены от реальных цен магазина;
9. какие коммерческие/открытые источники можно рассматривать;
10. можно ли построить каскад:

Россия → регион → город → магазин → персональная цена.

Не придумывай доступность API. Для каждого источника укажи фактический способ получения данных и ограничения.

# 7. ФОТО ЧЕКОВ

Исследуй опциональную функцию:

📸 Пользователь фотографирует чек.

Система пытается определить:

- магазин;
- дату;
- товар;
- количество;
- единицу измерения;
- цену;
- скидку;
- итог;
- категорию товара.

После распознавания пользователь подтверждает данные.

Исследуй:

- OCR;
- компьютерное зрение;
- LLM/VLM;
- существующие российские сервисы/API;
- форматы чеков;
- QR-код чека, если применимо;
- ФНС/ОФД и другие источники;
- стоимость и ограничения;
- приватность;
- хранение чеков;
- ошибки распознавания;
- необходимость подтверждения пользователем.

Не предлагай техническую реализацию без проверки существующих возможностей.

# 8. ПЕРСОНАЛЬНЫЕ ЦЕНЫ

Исследуй модель:

### Статистическая цена
Россия / регион / город.

### Цена магазина
Цена, обнаруженная в конкретном магазине.

### Цена пользователя
Фактические цены из чеков конкретного пользователя.

Нужно определить, как система должна выбирать цену при расчёте:

1. персональная;
2. магазин;
3. город;
4. регион;
5. Россия.

Проверь также необходимость хранения истории наблюдений:

Product → Price Observation → источник → магазин → дата → количество → цена.

Не называй отдельное наблюдение «ценой товара» без контекста.

Профиль

- упаковки;

- разные цены;
- отклонение фактических расходов от плановых.

# 11. ПСИХОЛОГИЯ ЧЕКОВ

Отдельно исследуй UX-проблему.

Пользователь может:

- не брать чеки;
- не хотеть их фотографировать;
- считать это лишним;
- не понимать пользу;
- воспринимать контроль расходов как неприятный или «мелочный».

Поэтому нельзя просто поставить кнопку:

«📸 Добавить чек»

Нужно исследовать способы донесения ценности.

Например:

> «Если иногда добавлять чеки, я смогу узнать твои реальные цены и точнее считать стоимость питания».

Исследуй:

- onboarding;
- мягкие contextual hints;
- progressive disclosure;
- персональные подсказки;
- frequency capping;
- отказ пользователя;
- повторное предложение только при наличии нового контекста;
- геймификацию без навязчивости.

Цель - не заставить фотографировать чеки, а показать, **какую практическую пользу пользователь получает взамен**.

# 12. ГЕЙМИФИКАЦИЯ

Исследуй, можно ли мягко стимулировать использование полезных функций.

Не превращай продукт в RPG.

Не вводи заранее:

- множество валют;
- очки за каждое действие;
- уровни ради уровней;
- искусственные задания.

Проверь, достаточно ли:

- прогресса;
- достижений;
- персональных инсайтов;
- экономии;
- точности персонального расчёта;
- целей;
- streaks;
- статусов.

Каждую механику обоснуй конкретной пользовательской ценностью.

Контекст проекта:

«Пухляш» - персональный помощник по питанию, покупкам, бюджету, рецептам, физической активности, целям и повседневным привычкам.

В проекте уже существует идея адаптивного помощника, который постепенно понимает контекст пользователя и помогает ему не через один фиксированный интерфейс, а через подходящий канал.

Предполагаемые каналы:

- Telegram - основной текстовый интерфейс, фото, уведомления, команды, взаимодействие с ботом.
- Telegram Mini App / Web App - полноценный визуальный интерфейс, графики, планы, настройки, подтверждения, работа с чеками и другими визуальными данными.

- Единое backend-ядро - общие данные, бизнес-правила, профиль пользователя, цели, питание, рецепты, бюджет, покупки, тренировки, чеки и т.д.

Ключевой принцип:

НЕ должно существовать трёх независимых «Пухляшей».

Telegram, Mini App и Алиса должны быть разными интерфейсами одного продукта и обращаться к единому доменному ядру.

При этом исследование должно определить, какие функции действительно должны существовать в каждом канале.

Список покупок| да| да| да| удобно получить голосом
Бюджет| да| да| осторожно| потенциально чувствительные данные
График расходов| нет/ограниченно| да| нет| нужен экран
План питания| да| да| частично| голос может озвучить краткое состояние
Тренировка| да| да| да| голос может быть полезен во время выполнения
Настройка профиля| да| да| ограниченно| много параметров
Разбор чека| да| да| нет| требуется изображение
Подтверждение покупки| да| да| да| можно голосом
Сложный план| да| да| нет| визуальный интерфейс лучше

Это только пример.

Не принимай эту таблицу как готовое решение.

Проведи собственный анализ.

---

3. ИССЛЕДОВАТЬ «ГОЛОСОВЫЕ МОМЕНТЫ»

Определи ситуации, когда пользователь физически занят и голос объективно удобнее интерфейса.

Например:

- готовит еду;
- идёт по магазину;
- занимается тренировкой;
- собирается на работу;
- находится на кухне;
- ведёт машину, если сценарий безопасен и допустим;
- хочет быстро узнать информацию;
- хочет быстро добавить продукт;
- хочет получить напоминание;
- хочет сообщить о выполненном действии.

Найди реальные сценарии, в которых голос сокращает количество действий.

Для каждого сценария описать:

1. Контекст.
2. Намерение пользователя.
3. Голосовая фраза.
4. Ответ Пухляша.
5. Нужно ли подтверждение.
6. Можно ли выполнить действие полностью голосом.
7. Нужно ли продолжение в Telegram/Mini App.
8. Что произойдёт с данными.

---

4. ПРОАНАЛИЗИРОВАТЬ ПРИМЕРЫ ДИАЛОГОВ

Разработай реалистичные голосовые диалоги.

Например:

Пользователь:

«Алиса, спроси Пухляша, что у меня сегодня на ужин».

Пухляш:

«Сегодня по плану курица с овощами. Хочешь, напомню продукты?»

---

Другой сценарий:

«Пухляш, добавь яйца в список покупок».

Ответ:

«Добавляю яйца. Сколько взять?»

Пользователь:

«Десять».

Пухляш:

«Готово, десять яиц добавлены».

---

Другой:

«Пухляш, я съел ужин».

Пухляш:

«Отметила ужин. Сегодня осталось...»

Исследуй десятки подобных сценариев.

Особенно интересны сценарии:

- питание;
- рецепты;
- продукты;
- список покупок;
- бюджет;
- цели;
- тренировки;
- напоминания;
- ежедневный check-in;
- эмоциональное/мотивационное сопровождение;
- взаимодействие с Ирисочкой.

---

5. ИССЛЕДОВАТЬ РОЛЬ ИРИСОЧКИ

Ирисочка - персонаж и помощник Пухляша.

Не делать её просто «голосом интерфейса».

Исследовать:

- должна ли Ирисочка говорить от своего имени;
- когда отвечает Пухляш;
- когда отвечает Ирисочка;
- могут ли они распределять роли;
- можно ли сделать разные типы взаимодействия;
- не будет ли это раздражать пользователя;
- как сохранить естественность;
- как избежать ощущения дешёвой маски над обычным чат-ботом.

Исследовать возможные модели:

1. Пухляш - система, Ирисочка - персонаж.
2. Ирисочка - основной голосовой помощник.
3. Пухляш и Ирисочка работают как дуэт.
4. Пользователь сам выбирает режим.
5. Система адаптирует формат общения по контексту.

Не выбирать вариант заранее.

Сравнить модели и показать их плюсы, минусы и ограничения.

---

6. АДАПТИВНЫЙ ПОМОЩНИК

Исследовать более важную концепцию:

Пользователь НЕ должен думать:

«Мне сейчас надо открыть Telegram».

Он должен думать:

«Мне нужно сказать Пухляшу».

А система уже выбирает подходящий канал.

Пример:

Пользователь:

«Пухляш, я купил продукты».

Система может ответить:

«Пришли чек в Telegram, я разберу покупки».

То есть голосовой интерфейс становится точкой входа, а не отдельным приложением.

Исследовать архитектуру такого поведения.

7. ЕДИНОЕ ЯДРО

Разработать концептуальную архитектуру:

              ПУХЛЯШ
                 │
    ┌────────────┼────────────┐
    ↓            ↓            ↓
Telegram      Mini App      Алиса
    │            │            │
 текст          UI           голос
 фото           графики      команды
 кнопки         формы        диалог
    └────────────┼────────────┘
                 ↓
          ЕДИНОЕ ЯДРО
                 ↓
    ┌────────────┼────────────┐

 Профиль      Питание       Рецепты
 Покупки      Бюджет        Цели
 Тренировки   Чеки          Напоминания

Но эту схему нужно критически проверить.

Исследовать:

- что должно быть общим;
- что относится к конкретному каналу;
- где должна находиться бизнес-логика;
- где должен находиться NLP / intent parsing;

- где должна находиться авторизация;
- где должна находиться история диалога;
- где хранить channel-specific state;
- как избежать дублирования логики.

8. АВТОРИЗАЦИЯ И СВЯЗКА АККАУНТОВ

Отдельно глубоко исследовать:

Telegram user
↓
account_id
↓
Puhlyash account
↑
│
Yandex/Alice account

Главный принцип:

Telegram user ≠ Alice user.

Один человек должен иметь возможность связать разные каналы с одной учётной записью Пухляша.

Исследовать:

- OAuth 2.0;
- account linking;
- access token;
- refresh token, если применимо;
- идентификаторы пользователя;
- хранение токенов;
- отзыв доступа;
- повторную авторизацию;
- отвязку аккаунта;
- что происходит при смене аккаунта;
- какие данные может получить навык;
- какие данные нельзя передавать.

Предложить безопасную модель account linking.

9. БЕЗОПАСНОСТЬ ГОЛОСОВОГО ИНТЕРФЕЙСА

Это обязательный раздел.

Рассмотреть сценарий:

Пользователь находится дома.

Рядом другой человек.

Пользователь говорит:

«Алиса, сколько я потратил в этом месяце?»

Нельзя автоматически предполагать, что голосовая среда является приватной.

Разделить операции минимум на:

🟢 Низкий риск

Можно выполнять/озвучивать без дополнительного подтверждения.

Например:

- рецепт;
- погода;
- общий совет;
- список обычных продуктов;
- что сегодня приготовить.

🟡 Средний риск

Требуется подтверждение.

Например:

- добавление покупки;
- изменение плана;
- изменение цели;
- изменение количества продуктов.

🟠 Высокий риск

Лучше перевести пользователя в Telegram/Mini App.

Например:

- подробный финансовый анализ;
- изменение важных персональных настроек;
- действия с большим количеством данных;
- операции, где требуется визуальное подтверждение.

🔴 Чувствительные данные

Исследовать, что вообще допустимо озвучивать голосом.

Например:

- доход;
- накопления;
- финансовые цели;
- подробные расходы;
- чувствительные сведения профиля.

Не придумывать юридические требования.

Проверить актуальные требования и документацию по источникам.

---

10. ГОЛОСОВОЕ ПОДТВЕРЖДЕНИЕ

Исследовать проблему:

«Пухляш, добавь молоко».

Можно ли сразу добавить?

А если:

«Пухляш, поставь цель накопить 100 000 рублей».

Нужно ли подтверждение?

А если:

«Пухляш, измени мой дневной лимит».

Нужен ли второй фактор / Telegram?

Разработать классификацию действий:

- read-only;
- reversible;
- low-impact write;
- high-impact write;
- sensitive.

Для каждой категории определить рекомендуемый механизм подтверждения.

---

11. ГОЛОС + TELEGRAM

Исследовать сценарии handoff.

Например:

Пользователь:

«Пухляш, разберём мои покупки».

Пухляш:

«Хорошо. Пришли фотографию чека в Telegram. Я распознаю покупки и покажу тебе результат перед добавлением в бюджет».

Или:

«У тебя есть несколько продуктов, которые нужно выбрать. Я отправила список в Telegram».

Исследовать:

- как пользователь понимает, куда перейти;
- как сохранить контекст;
- как продолжить разговор;
- как не заставлять пользователя повторять запрос;
- как связать voice session и Telegram session.

---

12. ГОЛОС + MINI APP

Исследовать сценарии:

«Покажи мой бюджет».

Вместо длинного голосового ответа:

«Я открыла твой бюджет в приложении».

Или:

«Пухляш, покажи мой план питания на неделю».

Голос должен выступать как точка входа в визуальный интерфейс.

Исследовать возможные модели deep-link / handoff и актуальные возможности платформ.

---

13. НАПОМИНАНИЯ И ПРОАКТИВНОСТЬ

Исследовать:

- может ли Пухляш напоминать о питании;
- тренировках;
- воде;
- покупках;
- целях;
- вечернем check-in;
- необходимости отправить чек;
- подготовке еды.

Особенно важно выяснить актуальные технические возможности Алисы в этой области.

Не предполагать наличие функции только потому, что она логично выглядит в продукте.

---

14. ЕЖЕДНЕВНЫЙ ГОЛОСОВОЙ CHECK-IN

Исследовать отдельный продуктовый сценарий:

Утром:

«Доброе утро. Сегодня у тебя по плану...»

Вечером:

«Как прошёл день?»

Пользователь:

«Нормально. На ужин съел не то, что было в плане».

Пухляш:

понимает контекст → фиксирует отклонение → при необходимости корректирует план.

Исследовать, насколько такой сценарий естественен и полезен.

---

15. НЕ ПРЕВРАЩАТЬ ПУХЛЯША В ГОЛОСОВОЙ CRM

Критически проверить продукт.

Не нужно делать голосовой интерфейс ради самого голосового интерфейса.

Для каждой функции задать вопрос:

«Почему пользователь захочет сделать это голосом?»

Если голос хуже кнопки или экрана - так и написать.

Особенно проверить:

- длинные ответы;
- таблицы;
- графики;
- сложные настройки;
- рецепты;
- планы;
- финансовые данные;
- списки из большого количества элементов.

---

16. ИССЛЕДОВАТЬ UX-ПРИНЦИП

Основная гипотеза:

Пухляш должен скрывать сложность.

Пользователь не должен знать:

- в каком сервисе находится функция;
- какой API вызывается;
- какой канал используется;
- где хранится информация;
- какая модель работает внутри.

Он просто говорит:

«Пухляш, помоги мне с ужином».

А система сама определяет:

- что пользователь хочет;
- какие данные нужны;
- нужно ли задавать вопрос;
- нужен ли голос;
- нужен ли Telegram;
- нужен ли Mini App;
- нужно ли подтверждение.

Проверить эту гипотезу.

17. КАРТА INTENT'ОВ

Но не ограничиваться этим списком.

Для каждого intent определить:

- параметры;
- обязательные параметры;
- необязательные параметры;
- возможные неоднозначности;
- необходимость подтверждения;
- допустимый канал;

- чувствительность данных;
- возможный fallback.

18. ОБРАБОТКА НЕОДНОЗНАЧНОСТЕЙ

Голос особенно подвержен неоднозначности.

Например:

«Добавь молоко».

Какое?

- обычное;
- безлактозное;
- 1 л;
- 2 л.

Система должна задавать минимально необходимый вопрос.

Исследовать принцип:

НЕ задавать пользователю пять вопросов подряд.

Вместо этого:

«Как обычно - литр обычного молока?»

Или использовать уже известный контекст пользователя, если это допустимо.

Исследовать, как адаптивный помощник может использовать историю без нарушения приватности.

---

19. КОНТЕКСТ И ПАМЯТЬ

Исследовать:

Что Пухляш должен помнить между каналами?

Например:

Пользователь в Telegram:

«Сегодня хочу что-нибудь с курицей».

Через час:

«Алиса, что приготовить?»

Может ли система понять, что речь о том же контексте?

Какие данные являются:

- session context;
- short-term context;
- long-term memory;
- user preferences;
- structured facts.

Не смешивать память ИИ с бизнес-данными.

Предложить архитектурное разделение.

---

20. MVP ГОЛОСОВОЙ ИНТЕГРАЦИИ

После исследования сформировать минимальный набор голосовых функций для первого эксперимента.

Не надо делать полноценную Алису.

Предложить минимальный эксперимент, который позволит проверить:

«Действительно ли пользователю нужен голосовой Пухляш?»

Например:

5-10 сценариев.

Определить:

- сценарии;
- необходимые backend-функции;
- какие данные нужны;
- критерии успешности;
- что измерять;
- какие гипотезы проверяются.

22. НЕОБХОДИМО ПРОВЕСТИ КРИТИЧЕСКИЙ АНАЛИЗ

Для каждого варианта определить признаки, при которых он становится вероятным.

ГЛАВНЫЙ ПРИНЦИП

Не исследуй «как прикрутить Алису к Пухляшу».

Исследуй:

«Как построить Пухляша, который умеет выбирать правильный способ взаимодействия с человеком».

Алиса - только один из каналов.

Telegram - другой.

Mini App - третий.

Главным объектом проектирования должно оставаться ЕДИНОЕ взаимодействие пользователя с Пухляшом, а не отдельные приложения.
