1. ПРАВИЛА ДОКАЗАТЕЛЬНОСТИ

1.1. Приоритет источников

Для текущего технического состояния

Используй только первичные источники:

1. "CODE" - фактический код;
2. "DATABASE" - фактическая схема и данные;
3. "RUNTIME" - реально работающий runtime;
4. "TEST" - фактические тесты и результаты их запуска;
5. "GIT" - commits, branch, diff, status;
6. "DOCUMENT" - документация и отчёты.

Сам аудируемый отчёт не является первичным источником текущего технического состояния.

Если отчёт говорит:

««31/31 тестов проходят»»

это только утверждение отчёта, пока оно не подтверждено "TEST".

Если отчёт говорит:

««C-2 не подключён к handlers»»

это только утверждение отчёта, пока это не подтверждено "CODE" / "RUNTIME".

---

1.2. Для продуктовых решений

Приоритет:

1. "OWNER" - прямое решение владельца продукта;
2. "DOCUMENT" - ранее зафиксированное решение;
3. "OBSERVATION" - наблюдение;
4. "INFERENCE" - вывод аудитора.

Старый документ не считать актуальным owner decision, если более новое прямое решение владельца ему противоречит.

3. ЖЁСТКОЕ РАЗДЕЛЕНИЕ ФАКТА И ИНТЕРПРЕТАЦИИ

Это обязательное правило всего аудита.

Для каждого существенного утверждения разделяй:

FACT:
что непосредственно подтверждается источником.

INTERPRETATION:
что из этого следует или что это может означать.

DECISION:
если действительно принято решение.

UNKNOWN:
если данных недостаточно для интерпретации.

Нельзя записывать интерпретацию как факт.

Пример

Неправильно:

«Recipes готовят пользователи, поэтому нужна таблица authors.»

Правильно:

FACT:
В текущей таблице recipes отсутствует author/owner.

INTERPRETATION:
Если появится подтверждённый UGC-сценарий, recipe domain, вероятно, потребует моделирования ownership.

STATUS:
UNKNOWN / SPEC

DECISION:
Не менять C-2 schema до Product Gate.

4. ПРАВИЛА ДЛЯ НЕДОСТУПНЫХ ИСТОЧНИКОВ

Если источник:

- отсутствует;
- не загружен;
- недоступен;
- не удалось прочитать;
- невозможно выполнить команду;
- невозможно проверить runtime;
- невозможно проверить БД;
- невозможно подтвердить тесты;
- источник противоречиво извлекается;

то:

ЗАПРЕЩЕНО

- считать утверждение подтверждённым;
- восстанавливать содержимое по памяти;
- делать вид, что источник был проверен;
- использовать сам аудируемый отчёт как замену первичному источнику;
- повышать confidence на основании косвенных признаков.

ОБЯЗАТЕЛЬНО

Создать:

[UNKNOWN]
Type: FACT
Statement: ...
Why: Первичный источник недоступен.
Evidence Checked: ...
Impact: ...
Can Defer: YES | NO
Next Action: Получить/проверить источник.

Если недоступен источник, но имеются независимые подтверждения из других источников, укажи это явно.

Пример:

FACT:
Таблица planner/... существует.
Source: CODE
Confidence: HIGH

UNKNOWN:
Невозможно подтвердить дату создания через GIT, поскольку git history недоступна.

Отсутствие одного источника не делает автоматически неизвестным весь факт, если тот же факт подтверждён другим первичным источником.

Правило доказательности

Используй единую таксономию.

[FACT]

Факт должен иметь:

Confidence: HIGH | MEDIUM | LOW
Source: CODE | DATABASE | RUNTIME | TEST | DOCUMENT | OWNER | OBSERVATION

Факт нельзя превращать в решение только потому, что он логичен.

[HYPOTHESIS]

Гипотеза должна иметь:

Confidence: HIGH | MEDIUM | LOW
Based on: ...

Гипотеза не является основанием для постоянной архитектуры без подтверждения.

[RECOMMENDATION]

Рекомендация эксперта.

Она не должна маскироваться под решение владельца продукта.

[DECISION]

Только принятое решение.

Обязательно:

Owner: PRODUCT | ARCHITECTURE | TECHNICAL
Basis: ...

[CONFLICT]

Используй:

Sources:
Conflict:
Impact:
Resolution:

[UNKNOWN]

Используй только эту форму:

[UNKNOWN]
Type: FACT | DECISION | SPEC | STALE | BLOCKER
Statement: ...
Why: ...
Evidence Checked: ...
Impact: LOW | MEDIUM | HIGH | CRITICAL
Can Defer: YES | NO
Next Action: ...

Не используй отдельные категории:

- MISSING FACT
- MISSING DECISION
- MISSING SPECIFICATION
- UNCONFIRMED
- STALE
- BLOCKER
- SAFETY UNKNOWN

Для них используй "[UNKNOWN]" с соответствующим "Type".

---

Важное правило по UNKNOWN

Если неизвестно, будут ли пользователи публиковать собственные рецепты, не записывай это как факт.

Правильно:

[UNKNOWN]
Type: FACT
Statement: Нет подтверждённых данных о том, будут ли пользователи регулярно публиковать собственные рецепты.
...

А отдельно можно указать:

[HYPOTHESIS]
Users will publish recipes.

Не смешивай неизвестность и гипотезу.
