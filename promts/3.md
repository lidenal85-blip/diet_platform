2. Исправить SoT для запроса «что есть сегодня»

Текущая формулировка недостаточно строгая.

Нельзя считать, что:

"meal_state WHERE tg_id=? AND day_date=today"

однозначно возвращает текущий план.

Каноническая цепочка должна быть:

"user → active diet_program → active weekly_plan → meal_state(day_date=today)"

То есть сначала определяется активная программа пользователя, затем активная неделя этой программы, и только после этого выбираются записи "meal_state".

Зафиксировать это как архитектурный инвариант и обновить соответствующие места документа, включая ADR/SoT/DoD/Failure Modes, если они сейчас описывают это иначе.

3. Активные сущности: физические DB-инварианты обязательны

Не оставлять это как «recommended/optional».

Для "diet_programs" обязательно предусмотреть физическое ограничение:

CREATE UNIQUE INDEX idx_one_active_program_per_user
ON diet_programs(tg_id)
WHERE status = 'active';

Для "weekly_plans":

CREATE UNIQUE INDEX idx_one_active_plan_per_program
ON weekly_plans(program_id)
WHERE status = 'active';

Кодовая проверка остаётся, но SQLite constraint/index должен быть последней линией защиты.

До реализации отдельно зафиксировать implementation precondition:

- проверить версию SQLite;
- проверить поддержку partial unique indexes;
- проверить эти индексы на копии БД/тестовой БД.

Если существующая SQLite-версия это поддерживает, не придумывать альтернативную архитектуру.

4. Чётко определить семантику meal_state

Не создавать автоматически «7 × 4 = 28» записей.

"meal_state" должен создаваться только для тех приёмов пищи, которые реально присутствуют в сгенерированном плане.

Например, если в конкретном дне есть только:

- breakfast
- lunch
- dinner

то создаются только эти три записи.

Не создавать искусственный "snack", который потом будет выглядеть как пропущенный приём пищи.

Зафиксировать:

"meal_state = materialized state только для фактически запланированных meal slots".

Обновить тестовые требования и DoD.

5. Не держать DB transaction во время LLM-вызова

Архитектура должна явно запрещать схему:

"BEGIN → LLM generation → DB writes → COMMIT"

Правильная схема:

"LLM generation → validation → BEGIN TRANSACTION → persist program/plan/meal_state/events → COMMIT"

То есть LLM вызывается ДО транзакции.

Транзакция защищает только атомарность сохранения уже подготовленных данных.

Если LLM завершился ошибкой, БД не должна находиться внутри незавершённой долгой транзакции.
