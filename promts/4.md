6. ACTIVE PROGRAM INVARIANT

Это обязательный DB-level invariant.

Создай:

CREATE UNIQUE INDEX idx_one_active_program_per_user
ON diet_programs(tg_id)
WHERE status = 'active';

Это не «рекомендация», а обязательная часть C-2.

Также добавь кодовую проверку там, где planner создаёт/активирует программу.

7. weekly_plans

Реализуй:

id TEXT PRIMARY KEY
program_id TEXT NOT NULL
tg_id TEXT NOT NULL
week_no INTEGER NOT NULL
start_date TEXT NOT NULL
end_date TEXT NOT NULL
days JSON

Обязательные инварианты:

Один active plan на одну программу:

CREATE UNIQUE INDEX idx_one_active_plan_per_program
ON weekly_plans(program_id)
WHERE status = 'active';

"start_date" и "end_date" обязательны.

Не полагайся только на application-level проверки.

8. meal_state

Реализуй:

id TEXT PRIMARY KEY
tg_id TEXT NOT NULL
plan_id TEXT NOT NULL
day_date TEXT NOT NULL
day_name TEXT
meal_slot breakfast|lunch|dinner|snack
planned_ref JSON
planned_text
status planned|eaten|skipped|replaced|missed
recipe_id nullable
replace_to JSON
note
updated_at

Обязательный constraint:

UNIQUE(plan_id, day_date, meal_slot)

Критически важно

"meal_state" создаётся только для реально существующих meal slots из generated plan.

Не создавай автоматически:

7 days × 4 meals

если в конкретном plan фактически нет snack или другого slot.

Никаких synthetic meal rows.

---

9. Canonical chain

Planner должен считать canonical relationship такой:

user
 ↓
active diet_program
 ↓
active weekly_plan
 ↓
meal_state

Функция вроде:

get_today_meals(...)

не должна искать meal_state только по:

WHERE tg_id = ? AND day_date = ?

Canonical lookup должен проходить через active program → active weekly plan → meal_state.

То есть пользовательский "tg_id" сам по себе не является достаточным SoT для выбора актуального плана.

Все ownership queries должны дополнительно проверять "tg_id".

Не реализуй scheduler/reminder logic.

Phase 0 здесь только про календарную семантику.

Meal slots
