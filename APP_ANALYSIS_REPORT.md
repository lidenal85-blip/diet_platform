## 1. Резюме (TL;DR)

«Пухляш» — Telegram-бот-ассистент по питанию: рецепты через LLM, подбор диеты опросником, недельный план, напоминания о приёмах пищи, фитнес-разминки, персонаж-саркастичный кот. Технически это **работающий MVP в одном процессе** (FastAPI + aiogram3 + APScheduler + SQLite) на сервере whimco.

Продукт действительно находится в состоянии «набор идей, не до конца сформированных», и у этого есть **пять измеримых причин** (все подтверждены кодом):

1. **Диета — одноразовый текст, а не объект.** Выбранная диета и недельный план показываются на экране и нигде не сохраняются → продукту нечего «помнить», все интеграции (рецепты ↔ диета ↔ фитнес) физически невозможны.
2. **Профиль пользователя не доходит до генераторов.** Вес, возраст, ограничения здоровья, регион есть в БД — но фитнес-движок и промпты рецептов их не читают → одинаковый контент для всех.
3. **Два онбординга не знают друг о друге** и пишут в одну таблицу → настройки размазаны по трём местам.
4. **Mascot-линейка наполовину пуста:** Ирисочка утверждена, но `modules/irisochka/` не существует.
5. **Контентный конвейер (поиск диет в интернете) остановился на модерации:** 12 диет в `pending_verification` с низким confidence, никто их не проверяет.

Хорошая новость: фундамент (LLM-слой с пулом ключей и фоллбэком, FSM, планировщик, пайплайн, свежий E2E-харнесс) качественный и аддитивно расширяемый. Ниже — детальный разбор и фазированная дорожная карта.

## 3. Как устроено сейчас

### 3.1 Слои

```
Telegram (long-polling)
   └─ bot.py: 8 роутеров в порядке: reactions → puhlyash_settings → meal_v2
      → cabinet → diet_picker → recipes → schedule(legacy) → general
Домены (modules/):
   ├─ recipes/     — генерация рецептов (LLMFactory), режимы quick/home/restaurant/pp
   ├─ fitness/     — упражнения-разминки (LLMFactory)
   ├─ puhlyash/    — персона: интро, рецепт дня, форматирование
   ├─ reactions/   — лайк/дизлайк/сохранить + inline-клавиатуры
   ├─ scheduler/   — APScheduler: напоминания о приёмах пищи
   ├─ notifier/    — короткоживущий aiogram Bot для фоновых отправок
   └─ search_gateway → web_scraper → diet_extractor → diet_registry
                      (поиск диет в интернете: Outbox-очередь в SQLite)
API (FastAPI :8150):
   ├─ delivery_api  — поиск/диеты/DLQ/health + worker loop
   ├─ cabinet_router, miniapp_router — WebApp-кабинет
Данные: SQLite WAL, 15+ таблиц
```

### 3.2 Данные

- **Пайплайн диет:** `search_sessions → outbox → dlq`, снапшоты страниц, `diet_drafts → diet_master` (source of truth: allowed/forbidden foods, contraindications, confidence, версии, аудит).
- **Пользователь:** `user_profiles` (~30 колонок после ALTER'ов), `meal_schedule` (v2), `recipe_sessions`, `shopping_lists`, `fridge_sessions`, `recipes`, `reactions`, `diary_entries`.
- **Важно:** `diet_master` со своей структурой (allowed_foods/forbidden_foods/conditions) — это **продуктовый актив, который ботом не используется**. Подбор диеты для пользователя (`diet_picker.py`) генерирует свой JSON мимо реестра.

### 3.3 LLM-слой

Все вызовы (после фиксов J2 и рефакторинга engine'ов) идут через `LLMFactory.execute_request()` — пул ключей, CircuitBreaker, Groq-fallback. Промпты переписаны без фигурных скобок (урок BUG-02). У `diet_picker.py` есть терпимый JSON-экстрактор и **эвристические фоллбэки** — пользователь не видит ошибку, если LLM недоступен. Это правильный паттерн; его нет только в старых местах (`generate_from_fridge`, `generate_budget_recipe` — там `json.loads` без защиты).

## 5. Главный диагноз: пять системных разрывов

### Разрыв 1. Диета — текст на экране, а не сущность

`diet_picker.py:chose_diet()` делает `UPDATE user_profiles SET active_diet_mode='home'` — и всё. Ни выбранная диета (карточки: name/calories/duration/pros/cons/key_foods), ни недельный план не сохраняются в БД. Последствия:

- продукт «забывает» диету сразу после показа; повторный заход = генерация заново (деньги и латентность);
- рецепты не могут «слушаться» диеты — им нечего читать;
- нет прогресса, нет истории, нет плана на весь срок (`duration_weeks` теряется);
- список покупок не связан с реальными рецептами (C1 из бэклога).

Это **корневая** причина ощущения «набора идей»: три домена (диета/рецепты/фитнес) существуют параллельно, без общего объекта-контракта.

### Разрыв 2. Профиль не доходит до генераторов

Проверено по коду:

- `modules/fitness/engine.py:generate_exercises(meal, diet_mode)` — не получает ни `weight_kg`, ни `health_notes`, ни возраст (E1 бэклога). Упражнения одинаковы для всех, включая людей с ограничениями здоровья — **это ещё и вопрос безопасности**.
- `modules/recipes/prompt_builder.py` читает только cook/budget/excluded — `goal` и `active_diet_mode` не используются (проверено grep'ом, зафиксировано в бэклоге K).
- `location` (регион) есть в профиле — в промпты не прокинут (F1): рецепты с недоступными продуктами.

### Разрыв 3. Размазанный профиль и онбординг

- **Два независимых онбординга** (`diet_picker` — цель/возраст/ограничения/активность; `cabinet` — кулинарный уровень/бюджет/исключения) пишут в одну `user_profiles`, не зная друг о друге (J4). Пользователь проходит один — второй молчит.
- Настройки живут в трёх местах: `cabinet.py`, `puhlyash_settings.py`, неявно в `meal_schedule_v2.py` (G2).
- Онбординг опционален и не требует заполнения профиля перед подбором диеты → промпт уходит с половиной данных.

### Разрыв 4. Маскоты: половина линейки отсутствует

- Ирисочка: персонаж утверждён (характер, зона «сладкое/десерты/утешение»), но `modules/irisochka/` **не существует**; mood="sweet" обрабатывает Пухляш (I1).
- Сарказм Пухляша не ограничен правилом «не выдумывай ингредиенты» (I2) — риск галлюцинаций в шутках.
- Заметка: `tests/test_puhlyash.py` проверяет Ирисочку через `modules.puhlyash.irisochka` — тесты и документация расходятся с реальной структурой (Ирисочка-модуль ждут в `modules/irisochka/`).

### Разрыв 5. Контентный конвейер простаивает

Пайплайн поиска диет (DuckDuckGo → scraper → extractor → `diet_master`) рабочий, но: 12 диет лежат в `pending_verification` с confidence 0.15–0.35 (ISSUE-06 — CircuitBreaker в момент retry деградировал извлечение), модерации нет. При этом `/diets` **показывает пользователям и неподтверждённые** диеты (fallback на pending) — с честной пометкой ⏳, но без верификации. Pipeline ждёт `/search` от пользователей, которые его почти не видят.

## 6. Детальный разрыв по доменам

### 🍝 Рецепты
- Сильные стороны: LLMFactory, режимы, профиль частично учитывается, реакции копятся.
- Пробелы: нет meal-prep (A1), нет генерации на неделю разом (A2), нет режима «Готовим с Пухляшом» (A3), список покупок не собирается из выбранных рецептов (C1), цель/диета не влияют на выдачу (K).

### 📊 Диеты
- Сильные стороны: флоу подбора работает и защищён фоллбэками; E2E.
- Пробелы: не сохраняется объект диеты (B3 — корневой), нет объяснения «почему эти продукты» (B2), нет дневника фактически съеденного (B1 — колонка `diary` в БД пустует), нет заметок/правок (B4), нет связи с `diet_master` (два параллельных мира диет).

### 💪 Фитнес
- Сильные стороны: концепция «офисная разминка, а не тренировка» (E2) уже реализована в промптах — правильный продуктовый выбор для маскота-лентяя.
- Пробелы: не видит пользователя (E1 — приоритет безопасности), нет отдельного «серьёзного» модуля (E3), блок упражнений вшит в каждое напоминание без тоггла (E4).

### ⏰ Расписание и локализация
- `AsyncIOScheduler(timezone="Europe/Moscow")` зашит жёстко; у пользователя нет `timezone` (F2) — напоминания уедут для всех не-московских.
- Напоминание безусловно склеивает рецепт + упражнения в одно сообщение (E4).

### 📱 WebApp / мини-апп
- ⚠️ **Найдено при анализе:** `/start` отправляет кнопку «📱 Открыть кабинет» с URL `https://leviathanstory.ru/diet/app?uid=...` (`bot.py`). Старый сервер недоступен → **кнопка ведёт в никуда**. Мини-апп-эндпоинты (`api/miniapp_router.py`) на whimco живут, но фронтенда на новом сервере нет.
- ⚠️ `miniapp_router` читает/пишет `user_profiles` по `tg_id` из query-параметра. Валидация Telegram `initData` (HMAC-подпись) в коде не видна — если её нет, профиль любого пользователя можно прочитать/перезаписать, угадав tg_id. Требует проверки и закрытия.

### 🧪 Тесты и качество
- Есть: юнит-тесты Пухляша/персоны, `tests/e2e_diet_picker.py` (E2E через реального диспетчера, фейковый транспорт, temp-копия БД).
- Нет: CI, smoke-гейта на импорт (аудит делался вручную), тестов пайплайна. ✅ `requirements.txt` создан 2026-09-12 (пины прод-venv whimco) — установка зависимостей воспроизводима.

## 8. Дорожная карта развития

Принцип: **сначала сделать данные настоящими, потом наращивать фичи**. Фазы соответствуют PRODUCT_BACKLOG, но переупорядочены под реальный критический путь (в бэклоге тоже честно указано: эпик K «физически невозможен без B3 и E1»).

### Фаза 0 — Гигиена (1–2 сессии, без новой логики)
1. **R2:** заменить WebApp URL на whimco (или отключить кнопку до появления фронтенда).
2. **R4:** перевесить API на `127.0.0.1` или закрыть firewall; healthcheck оставить локальным.
3. **R3:** проверить и закрыть авторизацию miniapp (валидация Telegram initData).
4. `requirements.txt` (+ версия в MANIFEST), почистить `*.bak/zip/env.bak`, удалить легаси `schedule.py` после проверки, что `meal_schedule_v2` покрывает всё.
5. Модерация 12 диет из `diet_master` (одобрить/отклонить) — разблокирует `/diets` как витрину верифицированного контента.
6. Синхронизировать TEAM_NOTES (ISSUE-03) с реальностью.

### Фаза 1 — Сделать диету объектом (ядро продукта; B3 + E1 + F1)
1. **Таблица `diet_program`**: tg_id, diet_name, source (llm/heuristic/registry), структура карточки, weeks (JSON: планы по неделям), status, created/updated. Выбор пользователя сохраняет сюда; `_get_week_plan` кэширует результат по неделе.
2. **Прокинуть профиль в промпты**: `generate_exercises(profile)` — вес/возраст/health_notes с жёсткими ограничениями интенсивности; `build_recipe_prompt` — goal/active_diet_mode/allowed-forbidden из `diet_program`; `location` — в оба.
3. Связать с `diet_master`: при подборе сначала искать в верифицированном реестре, LLM — только если нет совпадения (экономия ключей + контент становится переиспользуемым).

После этой фазы продукт перестаёт быть «набором идей»: появляется единственный объект, на который опираются все домены.

### Фаза 2 — Связный UX профиля (G1/G2/J4/E4/F2)
1. Единое меню «Профиль и настройки» (одна точка входа; кабинет/Пухляш/расписание — подразделы).
2. Один онбординг: анкета цели + кулинарная анкета последовательно, с возможностью «позже»; до заполнения — мягкое напоминание.
3. Тогглы дашборда: `show_exercises_in_meals` и будущие блоки по паттерну `notify_*`.
4. `timezone` (IANA) в профиле + per-user планирование (рефактор scheduler'а — закладывать сразу).

### Фаза 3 — Глубина продукта (A1/A2/A3/B1/B2/C1/I1/I2)
1. Дневник питания (B1): кнопка «Съел» из напоминания → `diary_entries` → следующий недельный план учитывает факт.
2. Ирисочка (I1): `modules/irisochka/persona.py` по образцу Пухляша; забрать «сладкое/читмил/утешение»; заодно I2 (границы сарказма) — правка SYS-промптов.
3. Список покупок из выбранных рецептов (C1) — теперь возможен, есть `diet_program` + рецепты недели.
4. Meal-prep и «неделя рецептов разом» (A1/A2), режим «Готовим с Пухляшом» (A3) — по готовности APScheduler-джобов.
5. B2 («почему эти продукты») — дешёвое улучшение доверия, просто поле в JSON-схеме.

### Фаза 4 — Платформенность (H1/H2/D1/K1 + устойчивость)
1. Экспорт «📥 Скачать мои данные» (H1) — JSON-файлом; retention-политика из бэклога (H2) — месячный APScheduler-job.
2. Пользовательские рецепты/упражнения + модерация (D1) — когда появятся активные пользователи, не раньше.

## 9. Как понять, что продукт «сложился»

Метрики, которые стоит начать считать уже сейчас (данных почти нет — `reactions`, `diary_entries` пусты):

1. **D7-retention** — возвращается ли пользователь через 7 дней после подбора диеты.
2. **Доля дошедших до конца онбординга → до «🚀 Подбирай!»** (воронка по шагам FSM).
3. **Реакции на рецепты** (лайк/дизлайк ratio) — качество LLM-контента.
4. **Выполнение напоминаний** — доля «Съел» после « время приёма пищи» (после B1).
5. Стоимость: LLM-вызовы на пользователя в день (лимиты Gemini/Groq при росте).

Целевая петля продукта, которая должна получиться: *подобрал диету → план на неделю сохранён → напоминания приносят рецепты, совместимые с диетой → отмечаю съеденное → следующая неделя адаптируется → список покупок собирается сам*. Сейчас существует только первое звено.
