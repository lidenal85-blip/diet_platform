## 1. Executive Summary

1. **FACT:** платформа навыков Алисы поддерживает всё ключевое для Пухляша: webhook-протокол с сервером разработчика, OAuth 2.0 authorization code + refresh token (account linking), состояние `state.session/user/application` (в т.ч. **между сессиями** для авторизованных пользователей — бета), surfaces с экраном и без.
2. **FACT:** публичных **push-уведомлений навыка по инициативе разработчика** в актуальной документации не найдено (в актуальном TOC `index.md`/`development` страниц про push нет). Проактивные напоминания — **OPEN QUESTION**, блокер для сценария «напоминания Алисой».
3. **HYPOTHESIS (сильная):** ценность Алисы для Пухляша = 5–8 «голосовых моментов» (готовит/магазин/тренировка), а не полная копия продукта. Условие (вариант B из §22 промпта).
4. **RECOMMENDATION:** строить не «навык Алисы», а **Capability Core**: реестр возможностей + интент-роутер + ядро домена, где Telegram/MiniApp/Alice = тонкие каналы. Часть A уже предложила registry — Part B расширяет его до мультиканального.
5. **RECOMMENDATION:** MVP-эксперимент — приватный навык с 5 сценариями read-only + 1 write с подтверждением; критерий успеха — частота выбора голоса vs Telegram.
6. **RECOMMENDATION:** сейчас НЕ реализовывать ничего (промпт §18/25); Gate-Alice — после «reader-first» UX и shopping v2.

## 4. Ограничения Алисы

- **FACT:** wake-word только «Алиса»; внутри сессии — ограниченная длительность (несколько ходов), потом завершение (`application.end_session`).
- **FACT:** голос не приватен по умолчанию (домашние колонки) — см. §11.
- **FACT:** длинные ответы неудобны голосом; списки/таблицы — только на экранах.
- **OPEN QUESTION:** лимиты на частоту вызовов webhook/задержки SLA — точные числа не зафиксированы в прочитанных страницах.

## 6. Голосовые сценарии (по образцу §3 промпта, 3 из ~20)

1. **«Алиса, спроси у Пухляша, что у меня сегодня на ужин»** → интент GET_SLOT(dinner) → `meal_state[today, dinner]` → «Сегодня по плану запечённая треска с салатом. Отметить?» → «Да» → `set_meal_status(eaten)`. Данные: read+write слота. Подтверждение: да (write).
2. **«…добавь яйца в список покупок»** → ADD_GROCERY(яйца) → уточнение минимально: «Десять как обычно?» (если есть история) → добавление в shopping v2. Подтверждение: да.
3. **«…я купил продукты»** → голос = точка входа: «Пришли чек в Telegram, разберу» → handoff (§15). 
4. Тренировка: «…начнём тренировку» → GET_WORKOUT(lunch) → пошаговое озвучивание.

## 7. Роль Ирисочки

- Модели (по промпту §5): 1) Пухляш-система/Ирисочка-персонаж; 2) Ирисочка=голос; 3) дуэт; 4) выбор пользователя; 5) адаптивно.
- **РЕКОМЕНДАЦИЯ:** в MVP — модель 1: Пухляш = функциональный ответ (все каналы), Ирисочка = тон/мотивация в Telegram (уже реализовано как персонаж `modules/puhlyash/persona.py` — FACT) и **не озвучивается в Алисе на MVP** (риск «дешёвой маски» + двойные личности в одном голосе). Переоценка — после Pilot-метрик.
- **HYPOTHESIS:** женский голосовой персонаж-дубль увеличит когнитивную нагрузку; проверять метрикой response rate, не «ощущениями».

## 9. Account Linking (безопасная модель)

**FACT (механика платформы):** Диалоги → сервер авторизации навыка (authorization code) → skill получает `session.user.access_token` на каждом запросе.
**RECOMMENDATION (модель Пухляша):**
1. `puhlyash_account` — каноническая сущность (не существует; НЕ создавать сейчас — только зафиксировать требование).
2. Telegram tg_id → аккаунт (создан при `/start` — уже де-факто аккаунт).
3. Навык при первом запросе: если `access_token` отсутствует/невалиден → карточка «Свяжите аккаунт» → OAuth-экран навыка → владелец логинится парой TG/код → сервер навыка связывает `yandex_uid ↔ account_id`.
4. Токены хранит только backend навыка; refresh по графику Диалогов (как работает OAuth grant — FACT).
5. Отзыв: выход в навыке (`#logout` есть в user-authorization.md) + отзыв на сервере Пухляша.
6. **Нельзя:** передавать health_notes в голосовой ответ; озвучивать чувствительные поля.

## 10. OAuth 2.0

- **FACT:** платформа требует authorization code grant (не implicit), refresh-токены поддерживаются; `meta.interfaces.account_linking` сообщает о доступности.
- **OPEN QUESTION:** актуальные требования к SSL/redirect-URL консоли Диалогов — при реализации сверить с консолью (страницы консоля менялись часто).

## 11. Безопасность голосового интерфейса (обязательный раздел)

| Уровень | Операции | Правило |
|---|---|---|
| 🟢 read-only, не чувствительные | «что на ужин», список покупок, рецепт-название, мотивация | озвучивать свободно |
| 🟡 low-impact write | добавить в список, отметить слот, изменить количество | голос + голосовое подтверждение |
| 🟠 high-impact write | изменение плана/цели, массовые операции | голос → handoff в Telegram (кнопка подтверждения) |
| 🔴 sensitive | суммы расходов, доход, health_notes, цели-деньги | **не озвучивать**; только TG/MiniApp; в голосе — «открыл в Telegram» |

**FACT-ограничение платформы:** навык не знает, кто слушает вокруг колонки — модель риска исходит из этого.

## 12. Уровни подтверждения

| Категория | Механизм |
|---|---|
| read-only | без подтверждения |
| reversible / low-impact | голосовое подтверждение («добавляю, ок?») |
| high-impact write | deep-link/handoff в TG + inline-подтверждение |
| sensitive | только в TG/MiniApp, голос лишь уведомляет |

## 13. Voice → Telegram handoff

**RECOMMENDATION:** маркер сессии в `state.session` (например `handoff: {topic, ts}`), при следующем открытии TG-бота бот предлагает продолжить («Продолжить разбор покупок?»). Реализация после Gate — через существующую FSM-механику TG.

## 14. Voice → Mini App handoff

- **FACT:** deep-link на навык (`skills-promotion-deeplink`) существует; обратный deep-link «навык → открытый Mini App» — **OPEN QUESTION** (проверять платформенные возможности при Gate).
- Fallback: голос говорит «открыл в Telegram» (уведомление в TG-бот с текстом/карточкой).

## 15. Контекст между каналами

- **FACT (платформа):** `state.user` сохраняется между сессиями у авторизованных (бета).
- **RECOMMENDATION:** session context — в state платформы; short-term (тема разговора) — `state.session`; долгая память — только в БД Пухляша (events/profiles). Не смешивать: бизнес-данные никогда не живут в state навыка.

## 16. Память

Разделение (по промпту §19): session / short-term / long-term / preferences / structured facts — см. §15. **FACT:** у Пухляша long-term уже = SQLite (profiles, meal_state, events); «память ИИ» отдельно не нужна MVP.

## 17. Intent-модель (каталог MVP)

Каталог стартовый (расширенный из промпта, только MVP-пометки):

```
GET_TODAY_PLAN, GET_SLOT(dinner), GET_RECIPE(link), MARK_MEAL_DONE,
CHECK_GROCERY_LIST, ADD_GROCERY, START_WORKOUT, GET_WORKOUT,
GET_PLAN_COST(coarse), START_DAILY_CHECKIN, OPEN_TELEGRAM(handoff)
```
Каждый intent: params/slots, ambiguity-политика («как обычно?»), confirm-уровень (§12), допустимые каналы. **RECOMMENDATION:** реализация интентов — в Capability Core (Part A §4), каналы лишь подставляют рендер.

## 18. Обработка неоднозначностей

Минимально необходимый вопрос + дефолт из контекста («Как обычно — литр обычного?»). **FACT:** персональный контекст «как обычно» требует Price/покупочной истории — её нет → в MVP дефолт = спросить.

## 19. Напоминания

- **FACT (внутр.):** напоминания Пухляша уже есть через Telegram (apscheduler, meal_schedule_v2, tz=Europe/Moscow) — работающий канал.
- **OPEN QUESTION (платформа):** активные push навыка Алисы — не подтверждены доками; до выяснения не проектировать напоминания-через-Алису. **Голосовой чек-in** = пользователь сам спрашивает («Алиса, спроси у Пухляша как мои дела») — работает без push.

## 20. Daily Check-in (голосовой)

**HYPOTHESIS:** утренний/вечерний check-in голосом естественен (готовит/собирается). MVP: read-only сводка + 1 write (отметить слот). Полный «понимание отклонений → корректировка плана» — позже (это adaptation-домен стратегии Phase 2+).

## 21. MVP голосового эксперимента

**Рекомендуемый MVP (5 сценариев, приватный навык):**
1. «Что сегодня по плану?» (read) 2. «Что на ужин?» (read) 3. «Я съел ужин» (write+confirm) 4. «Что в списке покупок?» (read) 5. «Начнём тренировку» (read+handoff).

Backend-функции: интент-роутер (общий с Помощником), доступ к meal_state/shopping, OAuth-связка. Измеряем: долю запросов, решённых голосом до конца; handoff-частоту; D7 двух групп (с навыком/без). Критерий успеха: ≥30% пользователей, связавших аккаунт, обращаются к навыку ≥3 раз/нед (**гипотеза-порог**).

## 22. Критический анализ: нужна ли Алиса (A/B/C)

| Сценарий | Признаки вероятности | Наша оценка |
|---|---|---|
| A: существенная ценность | пользователи «на ногах» (готовят/магазин), связка аккаунтов >50%, голос выигрывает у кнопок | **ASSUMPTION: маловероятно** при 2 тестовых пользователях |
| B: полезна узкой группе сценариев | 5–8 сценариев из §6 имеют устойчивый спрос | **HYPOTHESIS: наиболее вероятно** |
| C: не нужна (TG+MiniApp достаточно) | частота навыка <1/нед даже у связавших | возможно при текущем масштабе |
- **RECOMMENDATION:** не строить навык до (а) живого цикла reader-first, (б) shopping v2, (в) ≥10–20 активных пользователей; MVP — только после этого, приватным навыком.

## 23. Критические риски

1. Push-уведомления навыка недоступны → Алиса не канал проактивности (напоминания остаются в TG) — **архитектурное следствие, не блокер**.
2. OAuth-сервер навыка = отдельный компонент backend (SSL, endpoints) — стоимость Phase не нулевая.
3. Двойной туллинг (FSM TG + session Alice) — риск расхождения поведения; митигируется общим Capability Core.
4. Приватность: случайные свидетели у колонки; чувствительные данные — только визуальные каналы.
5. Голосовые сессии коротки — сложные сценарии (чеки) в голос не входят.

## 24. Что НЕ следует делать

Не делать «голосовой копии бота»; не озвучивать суммы/health_notes; не строить Ирисочку-голос в MVP; не проектировать напоминания-через-Алису до подтверждения push; не создавать account-сущности в БД «на всякий случай» (промпт §16/22).

## 25. Архитектурные рекомендации и следующий этап

- **R1:** Capability Core = единый интент-слой для Помощника (TG) и будущего навыка — проектируется сейчас (бумажно), реализуется в C-3 частично.
- **R2:** навык Алисы = тонкий адаптер: webhook → интент-роутер → домен → рендер; OAuth-сервер связки — отдельный маленький сервис.
- **R3:** при появлении push-возможности — переоценить проактивность.
- **Следующий этап (последовательность):** Gate-Alice решение владельца → техзадание приватного навыка (5 сценариев) → пилот → метрики → решение о развитии.
