## 3. ЭКРАН «СЕГОДНЯ»

- **Вызов:** кнопка «📅 Сегодня» в главном меню ИЛИ команда `/today` (`@router.message(F.text.in_({"📅 Сегодня", "/today"}))`). У хендлера нет `StateFilter` — кнопка срабатывает в любом состоянии диалога (заметка: во время FSM-сценария экран покажется поверх, состояние FSM не сбрасывается).
- **Данные:** `planner.get_today_meals(db, tg_id)` — единственный источник. Это canonical chain `user → active diet_program → active weekly_plan → meal_state(plan_id, day_date=today)` с tz-fallback `user_profiles.timezone → Europe/Moscow`. Никаких прямых `WHERE day_date=?` запросов.
- **Отображение:** `_render_screen()` — порядок приёмов как вернул planner (breakfast/lunch/dinner), для каждого: статус-эмодзи (⏳ planned / ✅ eaten / ⏭ skipped / 🔁 replaced / 💤 missed), `planned_text` (денормализованное блюдо из meal_state — фактическое поле, никаких выдуманных). Хвост: «✅ Съедено: N из M · осталось: K». Клавиатура: по 2 ряда на приём (✅ Съел/⏭ Пропустил; 🔁 Заменить/📖 Рецепт) + «🔄 Обновить» (`today:refresh`).
- **Пустое состояние:** `_empty_screen()` — «Активного плана пока нет 🤷‍♂️» + подсказка нажать «🎯 Подобрать диету». Генерация плана НЕ запускается (проверено тестом: `diet_programs/weekly_plans/meal_state` остаются пустыми).

## 4. ДЕЙСТВИЯ

- **eaten/skipped:** общий `_handle_status(call, "eaten"|"skipped")`. Порядок проверок: парсинг callback → `_fetch_meal` → **принадлежность** (`meal["tg_id"] != tg_id` → «Запись не найдена», без изменения) → no-op (`status == new_status` → «Уже отмечено ✅») → guard переходов (только `planned → eaten|skipped`; иначе «Статус уже изменён — обнови экран 🔄») → `planner.set_meal_status(db, plan_id, tg_id, day_date, meal_slot, status)` → событие → перерисовка экрана `_redraw()` (edit_text с новой клавиатурой).
- **Принадлежность записи:** чужой `tg_id` не проходит — тест подтверждает: статус остаётся `planned`, событий нет.
- **Повторные нажатия:** идемпотентны — `set_meal_status` не вызывается, `status_changed_at` не меняется, событие не дублируется (тест: ровно 1 событие после двух нажатий). Некорректный переход (eaten→skip) заблокирован guard'ом — вне переходов C-3.2 (замена через «🔁» — отдельный этап).
- **Событие `meal_status_changed`:** пишется через штатный `planner.log_event()` ТОЛЬКО при фактическом изменении. Props минимальны: `meal_state_id, plan_id, day_date, meal_slot, from_status, to_status`. Никаких health_notes, текстов блюд, данных профиля (тест проверяет отсутствие). Сбой логирования не отменяет отметку (own-try, конвенция diet_picker). Событие с успехом не пишется при неудаче (`set_meal_status` бросил → событий 0, тест).

## 5. «ЗАМЕНить» И «РЕЦЕПТ»

- **🔁 Заменить:** `call.answer("🔁 Замена блюд появится позже — сейчас просто отметь «✅ Съел» или «⏭ Пропустил»", show_alert=True)`. БД не трогается (`status=planned, replace_to IS NULL` у всех строк — тест), LLM не вызывается, событий нет.
- **📖 Рецепт:** без генерации и без новых LLM-вызовов. Если у слота есть `recipe_id` — показывается **сохранённый** рецепт из таблицы `recipes` (title/description/ingredients/steps, JSON-распарсинг с безопасным fallback); иначе честное «📖 Просмотр рецепта пока не подключён — придёт отдельным обновлением». Фиктивные рецепты не создаются. Тест подтверждает: сохранённый рецепт показан, записей в `recipes` не прибавилось.

## 9. ОСТАВШИЕСЯ ПРОБЛЕМЫ

1. **`RECIPES_SCHEMA` объявлен, но не исполняется `init_db()`** (предсуществующее): на свежей БД таблицы `recipes`/`fridge_sessions` не создадутся; в проде они исторические. Тест-фикстура компенсирует. Требует решения владельца в отдельном этапе (аддитивное включение в `init_db()` — 1 строка).
2. **Хендлер «Сегодня» без `StateFilter`** — кнопка отвечает в любом состоянии FSM. Сценарии не ломаются (state сохраняется), но при желании строгой изоляции добавить `StateFilter(None)` — решение владельца.
3. Vault-фейлы локальной регрессии — environmental (см. §6), не блокер.

## 10. СЛЕДУЮЩИЙ ШАГ
