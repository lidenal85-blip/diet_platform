## 4. Текущая архитектура чтения плана

- **Цепочка (PATCH-2, код):** `get_today_meals(db, tg_id, user_timezone)` → `get_active_program` → `get_active_plan` → `SELECT ... meal_state WHERE plan_id=? AND day_date=?` (сортировка breakfast→lunch→dinner→snack).
- **Даты:** `today_local(timezone)` из `user_profiles.timezone`; fallback Europe/Moscow только для пустого значения; неизвестная зона → `TimezoneError` (громкий отказ). В проде оба юзера Moscow.
- **День плана:** `day_date = plan.start_date + day_index` (PATCH-1); неделя валидна `end = start + 6` (код + partial unique index).
- **Гэп:** сегодня за пределами `[start_date, end_date]` активного плана → `get_today_meals` вернёт `[]` молча: UX не отличит «плана нет» от «план кончился». Для C-3 нужно различие (RECOMMENDATION: проверить `get_active_plan_for_user()` и вернуть отдельное сообщение «план закончился N дней назад»).
- **Гэп:** ридеров нет — экранов «Сегодня»/«Мой план» не существует.

## 5. Текущая архитектура отметок

- **Контракт:** `set_meal_status(db, plan_id, tg_id, day_date, meal_slot, status, *, replace_to=None, note=None)` — идемпотентен по своей природе (UPDATE по уникальному ключу; повторное нажатие той же кнопки даёт тот же результат, rowcount 1). `status_changed_at` = UTC.
- **VALID статусы:** `planned/eaten/skipped/replaced/missed`.
- **Переходы:** **никак не ограничены** — из любого в любой (HYPOTHESIS: для C-3 это ок; «передумел» — легальная ветка, пометка missed не нужна в UI).
- **replaced:** `replace_to` (JSON dict) + `note` — поля готовы, семантика замены (что подставить) не реализована нигде (UNKNOWN: формат `replace_to` — dict `{"text": ...}`? решается в реализации).
- **События:** `plan_viewed` доступен; отметки — нет (см. §7-1).
- **Собеседник-писатель в проде:** `persist_plan_bundle` (diet_picker.py:471) — единственный writer meal_state; статусы в проде: 28 × planned.

## 6. Текущая архитектура рецептов

- **Таблица recipes** (database.py:148): id/title/mode/description/ingredients(JSON)/steps(JSON)/КБЖУ/tags/source — зрелая, 80 строк в проде, 5 потоков генерации (engine.py: `generate_recipe(query, mode, profile)`, `generate_from_fridge`, `generate_budget_recipe`).
- **Writer:** `_save()` в recipes.py — `INSERT OR IGNORE` (дедуп только по PK uuid; **семантического дедупа нет** — тот же запрос сгенерирует новый рецепт).
- **Связь с планом:** нулевая — `recipe_id` в meal_state всегда NULL; planned_text — строка вида «Гречка с курицей и овощами»; recipes хранит title/description, но **поиска по названию блюда нет** (нет SELECT по title-подобию).
- **Повторное открытие:** в потоке «Рецепты» каждый раз = новый LLM-вызов. Для блюд плана C-3 обязан использовать `recipe_id` → `SELECT * FROM recipes WHERE id=?` → `_fmt()` (готовый рендер) — 0 LLM.
- **LLM-стратегия (HYPOTHESIS→DECISION владелец):** при первом «Рецепт» для planned-блюда: (a) точный матч по title в recipes — берём; (b) иначе 1 LLM-вызов `generate_recipe(planned_text)` + `_save()` + `UPDATE meal_state SET recipe_id` — связь навсегда, повторы бесплатны.

## 7. Проблемы и конфликты

1. **CONFLICT: закрытая таксономия против C-3-отметок.** `log_event` громко отказывает на `meal_eaten`. Варианты: (a) не логировать статусы в events (только `status_changed_at` в meal_state — нулевой код), (b) аддитивно расширить PHASE0_EVENTS на `meal_status_changed` (одна строка + тест). Рекомендую (b): аналитика eaten-rate — ядро будущей адаптации; политика CP-2 позволяет доменные префиксы аддитивно.
2. **CONFLICT: дрейф клавиатур.** 3 копии main-клавиатуры (bot.py, recipes.py — с лишней кнопкой «🐈 Пухляш», diet_picker). Меню C-3 правим в трёх местах или вводим единый `bot_handlers/keyboards.py`. RECOMMENDATION: единый модуль (одно изменение SoT), иначе дрейф продолжится.
3. **Проблема: «Расписание» vs «Сегодня» семантически конфликтуют** для пользователя: «Расписание» = собственные приёмы (user_meals, legacy-поток с LLM-«загрузкой стандартного»), «Сегодня» = блюда из активного плана. RECOMMENDATION: C-3 не трогает «Расписание» (scope-дисциплина); в меню C-3 кнопка «Сегодня» идёт первой, «Расписание» остаётся на месте до Phase 1-решения (решение владельца §12-3).
4. **Проблема: границы плана.** Просмотр «Сегодня» после 2026-09-23 → пустой экран без объяснения (см. §4). Обязательно обработать в UX.
5. **Проблема: длина сообщений.** Полный план 7 дней × 4 приёма в одном сообщении > 4096 символов. diet_picker уже режет на 3800; для «Мой план» нужен либо чанк-вывод, либо inline-пагинация по дням (RECOMMENDATION: inline-пагинация день ← →, заодно готовит «Рецепт»-кнопки).
6. **UNKNOWN: тесты handlers.** e2e-харнесс покрывает diet-picker, но клавиатурных/колбечных тестов нет; как тестировать new handlers — см. §10.
7. **UNKNOWN: prod-запуск handler-файлов.** Проверено включение роутеров (bot.py:423–433: reactions, puhlyash, meal_v2, cabinet, picker, recipes, schedule, common). Новый router «Сегодня/План» встанет по той же схеме; риск 注册 конфликтов — низкий (префиксы свободны).

## 10. Тесты и критерии приёмки

**Новые юнит-тесты:**
- `set_meal_status`: happy-path eaten/skipped/replaced (+replace_to/note сохранение), идемпотентность (двойной вызов → одна строка, status_changed_at обновлён), невалидный статус/слот/дата → SlotsError, wrong-user/wrong-plan → rowcount=0 → None.
- `get_today_meals` границы: план кончился → [], план не начался → [].
- `keyboards`: отсутствие дрейфа (строки кнопок фиксированы).
- handlers: колбэк eat → статус в БД (aiosqlite tmp-бд, fake Message/CallbackQuery — паттерн уже есть в test_diet_picker_wiring).
- recipe-link: существующий рецепт → 0 LLM-вызовов (мок engine); отсутствующий → 1 вызов → 1 строка recipes → recipe_id установлен; повтор → 0 вызовов.
- events: `meal_status_changed` логируется, health_notes-защита остаётся.

**Регресс (должен пройти целиком):** текущие 86 (test_planner_phase0 34 — инварианты цепочки; test_diet_picker_wiring — persist-поток; e2e_diet_picker `--fast`).

**Приёмка C-3 (по промпту):** 6 сценариев из §Критерий — руками на проде после деплоя + e2e-харнесс расширяется пунктами: открыть сегодня → eat → повторный просмотр → рецепт → повторный рецепт (0 новых LLM) → перезапуск бота → данные на месте.

## 11. Риски миграций и совместимости

- **Миграций нет.** Все нужные колонки/таблицы/индексы существуют в проде (verified). Риск = 0.
- **Совместимость:** legacy «Расписание» (user_meals) не трогаем — потоки не пересекаются (разные таблицы, разные кнопки). «Пухляш»-настройка (ph:*) не трогаем.
- **Риск 1:** дрейф клавиатур при правках в 3 файлах → митигируется keyboards.py (§7-2).
- **Риск 2:** гонка двойного клика «Рецепт» → двойной LLM-вызов → митигируется UPDATE-guard (§9-Шаг 4) + дешёвый probe.
- **Риск 3:** edit_text колбэков при старых сообщениях (>48h) упадёт — обёртка try/except → answer new message.
- **Риск 4:** замен-UX не решён (UNKNOWN §8) — C-3.4 может застрять; mitigate: минимальный вариант (1 LLM-подсказка) или отложить replaced-кнопку на C-3.5 (решение владельца).
