## 1. КРАТКИЙ ВЫВОД

1. **FACT:** меню подтверждает гипотезу дублирования — 6 из 11 кнопок главного меню — рецептурная группа («🍝 Рецепт от Пухляша», «👨‍🍳 Рецепты», «🧊 Холодильник», «💰 По бюджету», «🐈 Пухляш», частично «ℹ️ Помощь»), при этом «что сегодня по плану», «мой план», «покупки» отсутствуют как кнопки вовсе.
2. **FACT:** ценность не в новых кнопках, а в закрытии разрыва данных: план материализован (28 meal_state), но не читается; список покупок — строки-текст; цены отсутствуют (C-2.3).
3. **РЕКОМЕНДАЦИЯ:** новая ИА «Главная/Сегодня + 5 разделов» с единым Capability Registry — гипотеза промпта подтверждается, но без новых доменов: реестр = таблица соответствий intent→capability→handler, не бизнес-логика.
4. **FACT:** Budget-блок в текущем проде невозможен в полном виде — нет продуктов, цен, чеков. Минимальная модель: стоимость плана = Σ (структурированный shopping v2 × статистическая цена).
5. **FACT:** цены по России: официальный источник средних цен существует (ЕМИСС/fedstat.ru — портал жив, проверен HTTP 200); реальных магазинных/персональных цен без чеков нет — каскад Россия→регион→город→магазин→персональная строится только с Price Observations из чеков.
6. **FACT:** фото чеков технически осуществимо (QR чека РФ несёт ФН/ФД/ФПД), но текущая доступность public API ФНС/ОФД — **НЕИЗВЕСТНО** (требует отдельной проверки), OCR/VLM через LLMFactory — технически готов (пул Gemini), стоимость — оценочно.
7. **ГИПОТЕЗА (промпта):** «Пухляш = навигационный слой» — подтверждается частично: навигация нужна, но первым шагом должен стать **дата-фид «Сегодня»** (план/слоты/покупки), иначе помощнику нечего навигировать.
8. **FACT:** Mini App в Phase 0 отключён (ADR, routes disabled, тест `test_miniapp_disabled.py`) — вся новая ИА проектируется **Telegram-first**; Mini App — отдельный Gate.
9. **РЕКОМЕНДАЦИЯ:** порядок работ: (1) reader-first «Сегодня» + покупки из плана → (2) Capability Registry + интент-роутер → (3) shopping v2 → (4) Budget MVP (статистические цены) → (5) чеки (optional, отдельный Gate).
10. **FACT:** геймификация — только прогресс/инсайты (стрик «всё по плану», «экономия недели»), без валют/уровней; реакций в проде 1 на 80 рецептов — механики вовлечения не работают и строить их до живого цикла бессмысленно.

## 3. НОВАЯ ИНФОРМАЦИОННАЯ АРХИТЕКТУРА

**РЕШЕНИЕ (предложение, не реализация):**

```
🏠 Главная / Сегодня (динамическая сводка)
├── 👤 Кабинет          ← текущий cabinet + diet_picker-анкеты (объединить доступ)
├── 🍽 Питание          ← «🎯 Подобрать диету», «📅 Мой план» (NEW reader), «⏰ Расписание»,
│                          «🍳 Сегодня» (NEW: слоты+отметки eaten/skipped)
├── 👨‍🍳 Рецепты         ← «Рецепты», «Холодильник», «Ужин на сумму» (быв. «По бюджету»),
│                          «Рецепт от Пухляша» (→ внутрь, не отдельная кнопка)
├── 💪 Фитнес          ← существующий modules/fitness (сегодня только в напоминаниях!)
├── 💰 Бюджет          ← Phase-минимум: «Стоимость плана», «🛒 Покупки»; чеки/расходы — позже (Gate)
└── 🔍 Помощник         ← свободный запрос: интент-роутер по Capability Registry
```

| Раздел | Что переезжает | Что удаляется как дубль | Что становится контекстным |
|---|---|---|---|
| Питание | diet_picker FSM, расписание | — | «Сегодня» показывается при активном плане |
| Рецепты | все 4 рецептурных потока | 4 кнопки → 1 раздел | «рецепт для блюда из плана» (после recipe-link) |
| Бюджет | «По бюджету» → «Ужин на сумму» | — | Стоимость недели появляется при shopping v2 |
| Помощник | — | «ℹ️ Помощь» (статичный текст) | ответы на произвольные запросы |

**FACT:** все перемещения — над существующими handler'ами; новые сущности не нужны (кроме таблицы registry — см. §4).

## 4. АДАПТИВНЫЙ ПОМОЩНИК

**Модель (РЕКОМЕНДАЦИЯ):** Capability Registry + intent-роутер + канальные карточки.

```
capability_registry:
  id, title, description, phrases[](примеры), section, handler_ref,
  requires (active_plan? profile?), risk_level(read/low/high), channel[]  ← каналы: Phase 0 = telegram
intent_router(text):                      # LLM один вызов: text → {capability_id, slots}
  1. матч по phrases (дёшево, без LLM)
  2. LLM-классификация по реестру (fallback)
  3. LOW-CONFIDENCE → «уточняющий вопрос» или топ-3 варианта кнопками
```

- **FACT:** LLMFactory уже даёт структурированные вызовы (task_type='structured') — классификатор на 1 flash-lite вызов вписывается в бюджет (C-2.3 §5: LLM-бюджет минимален).
- **ГИПОТЕЗА (проверка в MVP):** ≥70% типовых запросов покрываются матч-фразами без LLM.
- «Учёт использованных функций» — **FACT:** events-таблица уже пишется (onboarding/diet_program/plan_viewed) — канал для adaptive hints уже есть. Frequency capping — свойство hints, не новой таблицы.
- **НЕИЗВЕСТНО:** retention-эффект помощника — проверяется только экспериментом.

## 5. УМНЫЙ ПОИСК

Модель = §4 (реестр + контекст пользователя + LLM-фоллбэк). Примеры покрытия:

| Запрос | Механика | LLM? |
|---|---|---|
| «Что сегодня по плану?» | INTENT today_plan → meal_state по today | нет (после reader-first) |
| «Сколько обойдётся диета?» | INTENT plan_cost → shopping×цены (после Budget MVP) | нет |
| «Осталось 2500₽ до зарплаты» | не питается данными → честный ответ + раздел Бюджет | 1 вызов |
| «Рецепт из того, что есть» | INTENT fridge → существующий fridge-flow | существующий генератор |
| «Где мои тренировки?» | INTENT fitness_today → fitness-модуль | нет |

**FACT:** «Я забыл, где список покупок» сегодня технически неотвечаем (списка-сущности нет) — поиск не маскирует пробелы данных.

## 6. БЮДЖЕТ

**FACT (C-2.3):** расчётов стоимости нет; есть только `budget_level` (подсказка) и «ужин на сумму».

**Минимальная полезная модель (РЕКОМЕНДАЦИЯ, три слоя):**
1. **План → Список:** shopping v2 (items: name/qty/unit/category) — без него бюджет невозможен.
2. **Список → Стоимость:** цена уровня «город» (статистика) × qty; упаковки как min(шт×объём, упаковка) — **ГИПОТЕЗА, требует теста на реальных корзинах**.
3. **Факт → Наблюдения:** чеки (optional) → Price Observations → персональная цена вытесняет статистическую.

Что заранее: стоимость плана, список. Что фактически: покупки/чеки. Учёт «уже дома» (pantry) — Phase за Budget MVP (стратегия §265 — FACT из доктрин).

## 7. ЦЕНЫ

| Уровень | Источник | Статус |
|---|---|---|
| Россия/регион/город — статистика | **ЕМИСС (fedstat.ru)** — проверен HTTP 200, порог «indicator/…»; официальные средние потребительские цены Росстата | **FACT:** портал жив. **OPEN QUESTION:** актуальные требования API-доступа (токен/лимиты) — проверять на этапе Budget MVP |
| Магазин | прайсы/чеки сетей | **НЕИЗВЕСТНО** без чеков; скрейп — хрупко и юридически серо (РЕШЕНИЕ: не делать) |
| Персональная | чеки пользователя → Price Observation (product, store, date, qty, price) | Модель ясна (промпт §8); включение — отдельный Gate |

- Статистическая цена vs магазинная: статистика — «средняя по чеку города», годится для ориентира ±20–30% (**ГИПОТЕЗА**), не для «сколько я заплачу точно».
- Каскад Россия→регион→город→магазин→персональная — **РЕКОМЕНДАЦИЯ:** строить постепенно, каждый уровень замещает предыдущий только при наличии данных (fallback вниз).

## 8. ЧЕКИ

| Вопрос | Статус |
|---|---|
| QR чека РФ | **FACT:** QR несёт реквизиты (ФН/ФД/ФПД/сумма/дата) — этого достаточно для запроса позиций по OFD |
| Публичная доступность API ФНС/ОФД сегодня | **НЕИЗВЕСТНО** — официальный публичный API неоднократно менял статус; требует целевой проверки до любого проектирования |
| OCR/VLM без QR (фото полки/чека) | **FACT:** техвозможность есть (мультимодальные LLM в пуле); качество на чеках РФ — **НЕИЗВЕСТНО**, нужен пилот на 20–30 фото |
| Подтверждение пользователем | **РЕКОМЕНДАЦИЯ:** обязательно (UI: «распознал — поправь — сохрани») |
| Приватность | чеки = покупки+место; хранить извлечённые наблюдения, не сырые фото (по умолчанию) |
| UX-психология (промпт §11) | не кнопка «📸 Чек», а value-first: «Добавишь чек — посчитаю твои реальные цены» после 1–2 покупок; frequency cap по events |

**РЕШЕНИЕ:** чеки — вне Phase 0/1; отдельный Product Gate после Budget MVP.
