## 1. Стратегическая формулировка

### 1.1 Product Definition

> **«Пухляш» — это Telegram-система, которая сама организует питание пользователя на неделю вперед и ведёт его состояние между приёмами пищи, чтобы человеку не приходилось ни считать, ни решать, ни записывать.**

(Персонажи — форма, в которой система говорит; см. §6.)

### 1.2 Core Problem (job-to-be-done)

> **Когда** рабочий день заканчивается и наступает время есть, **человек хочет** просто поесть то, что соответствует его цели, **но** план остался в виде текста неделю назад, еда в холодильнике не совпадает с планом, а трекеры требуют взвешивать и записывать, **поэтому** он решает заново, срывается или заказывает — и цель отодвигается ещё на неделю.

Более короткая формула боли: *«Знаю, как надо. Не могу организовать в реальной жизни без ежедневного усилия»*. Это HYPOTHESIS H1 из Stage 1 (за неё: боли §6 Stage 1, отзывы ETM; против: всего 2 пользователя — проверяется метриками §11).

### 1.3 Core Value Proposition

| Слой | Что получает пользователь |
|---|---|
| **FUNCTIONAL** | Понятный план на неделю → напоминание в нужный момент → один тап «съел / заменил / не успел» → следующий план уже учитывает это. Ноль подсчётов, ноль ввода граммов. |
| **EMOTIONAL** | Никто не ругает за срыв. Пухляш реагирует по-человечески («бывает, вот быстрый вариант на вечер»), Ирисочка объясняет, не стыдя. Питание перестаёт быть экзаменом. |
| **BEHAVIORAL** | Снижение числа ежедневных решений о еде до ~1 (подтвердить/заменить). Пропуск — не конец диеты, а входная точка адаптации. |

### 1.4 Что НЕ является продуктом (границы + обоснование)

| Не является | Почему (стратегическое, не вкусовое) |
|---|---|
| **Calorie tracker** | Строки «calorie/macro/photo logging» в Feature Matrix = 0 и заполнять их не будем: tracking-полюс рынка перегрет (Cal AI, MFP), а наши боли (вина, ввод) трекингом усиливаются. Строить = конкурировать без бюджета там, где у нас 0. |
| **Медицинская система** | LLM-контент без клинической валидации. Граница фиксируется UX: дисклеймеры, отказ от «лечебных» обещаний, мягкие формулировки. Иначе — юридический и репутационный риск. |
| **Cookbook** | Рецепты — не контент-библиотека, а исполнение плана. Рецепт без связи с планом/покупками не создаёт retention (61 рецепт в БД, 1 реакция — FACT, подтверждающий). |
| **AI chatbot** | Чат «Шеф на телефоне» — вспомогательный режим, не ядро. Чат без состояния = ChatGPT, у которого нет шансов. |
| **Соцсеть / community** | При 2 пользователях любые social-механики преждевременны (PARK до Phase 5+). |

## 2. Product Core

Проверка схемы из промта: базовая цепочка подтверждается аудитом (разрыв именно в «Diet Program → Meal → Reaction»), но в неё нужно добавить **три сущности без которых петля не работает**: `Deviation` (отклонение от плана — иначе адаптации не на чем), `Pantry` (иначе замены не соответствуют реальности — необязательно в ядре), `CharacterMemory` (отдельный bounded context, см. §7). Схема ниже — каноническая:

```
User → Profile → Goal → Diet Program → Weekly Plan → Meal → Recipe
                                    ↓                      ↓
                              Reminder ←──────────── (время)
                                    ↓
                              User Reaction (съел/не съел/заменил)
                                    ↓
                              Deviation (что и почему отклонилось)
                                    ↓
                              Adaptation → Next Weekly Plan
                                    ↘
                              Character Memory (персонажи помнят и ссылаются)
```

### CORE (без этого продукта нет)
1. **Profile** (canonical, один онбординг: цель, вес/возраст/ограничения, кулинарный уровень, регион, timezone).
2. **Diet Program** (сохранённый объект: структура + weeks; выбор пользователя живёт в БД, не на экране).
3. **Weekly Plan** (7 дней × приёмы, привязан к Diet Program).
4. **Meal State** (плановый приём пищи + его фактический статус: planned/eaten/skipped/replaced).
5. **Reminder** (плановое время → сообщение → реакция).
6. **Reaction/Deviation** (минимальная фиксация факта и причины).
7. **Adaptation** (следующая неделя строится с учётом истории).

### SUPPORT (усиливает core)
- Recipe Engine (уже есть — FACT), Reactions на рецепты (есть), Fridge/Pantry, Shopping List, Budget, Character Layer (vibes/mood), аналитика событий.

### OPTIONAL (позже)
- Mini App, progress/вес-трекинг, world/lore, community, monetization, wearables, restaurant-режим как домен.

## 3. Основная User Loop

Спроектированный идеальный цикл (принцип: **минимум ввода, максимум контекста**):

```
УТРО
  Пухляш: «Доброе! Сегодня по плану овсянка с бананом, 10 минут.
          Вечером — курица с гречкой, ингредиенты из твоего списка.»
  (план известен системе — пользователь ничего не открывает)
  → пользователь может тапнуть «приготовить» или промолчать

ДЕНЬ / время приёма
  Reminder: «🍽 Обед по плану: курица+гречка. Съел?»
  → [✅ Съел] [🔄 Заменить] [❌ Не успел]
  Замена → 3 быстрых варианта (по профилю/холодильнику/бюджету), 1 тап
  Пропуск → «Ок. Ужин тогда полегче?» → [Да] [Нет]

ВЕЧЕР
  Никаких подсчётов. Итог дня система знает сама.

КОНЕЦ НЕДЕЛИ
  Ирисочка: «Из 19 приёмов 15 по плану. Завтраки часто пропускаешь —
  сделаю их проще и быстрее. Гречку заменим, ты её дважды отложил.»
  → новая неделя сформулирована ПО ПРИЧИНЕ поведения
```

**FACT-проверка петли против текущего кода:** сейчас существуют только «План» (неперсистентный) и «Reminder» (не связан с планом). Всё между ними — строительная площадка. Петля спроектирована так, что каждый её узел = событие аналитики (§11).

## 4. Фундаментальный UX-принцип: «Система ведёт состояние»

Проверка гипотезы промта: **принимается как фундаментальный принцип.**

Обоснование: главные боли Stage 1 — ввод (5–10 мин/день), вина, decision fatigue. Все три снимаются инверсией ответственности: не человек ведёт записи для системы, а система ведёт состояние для человека. Диалог «Съел? → Да/Нет/Заменил» — это один тап против 5–10 минут логирования; он же даёт системе главные данные для адаптации.

**Правила принципа (для всех будущих фич):**
1. Если фича требует от пользователя записи/подсчёта — ищем способ определять это из контекста или спрашивать одним тапом.
2. Пропуск — не ошибка, а сигнал: система первая предлагает смягчение.
3. Каждый вопрос пользователю должен иметь кнопку-ответ; свободный ввод — опция, не требование.
4. Система не показывает «остаток калорий» и не стыдит цифрами — состояние выражается в планах, а не в метриках.

*Верификация принципа = H9 из Stage 1 (≥40% активных отвечают на «Съел?») — метрика стоит в §11.*

## 5. Персонажи

### Пухляш (основной персонаж-носитель планирования)

| Атрибут | Определение |
|---|---|
| **Роль** | «Старший брат по еде»: ведёт план, предлагает, подхватывает при срыве. |
| **Ценности** | Еда — удовольствие и забота, не экзамен. Реальная жизнь > идеального плана. |
| **Сильные стороны** | Знает, что сегодня по плану; всегда имеет запасной вариант; никогда не осуждает. |
| **Слабости** (очеловечивающие) | Сам любит поесть; ленится готовить долго; не силён в тонкостях БЖУ. |
| **Отношение к еде** | Восторженно-практичное: вкусно, просто, из обычного супермаркета. |
| **Отношение к пользователю** | «Мы с тобой вместе», не «я тебя исправляю». |
| **Отношение к Ирисочке** | Уважает её знания, слегка побаивается её замечаний, благодарит за подстраховку. |
| **Стиль речи** | Разговорный, короткие фразы, лёгкая самоирония, без сарказма-жалости. |
| **Юмор** | Только про то, что реально есть в рецепте/диалоге (правило I2); ≤1 шутка на сообщение. |
| **Границы** | Не даёт медицинских советов; при словах «болезнь/лекарства/расстройство» передаёт Ирисочке + дисклеймер «не замена врачу». |
| **Что помнит** | План недели, что съедено/пропущено, 3–5 последних замен и отказов, любимые блюда, имя/цель. |
| **Что никогда не забывает** | Непереносимости и аллергии (hard rule в каждом промпте), заявленные ограничения здоровья, попрос пользователя «не предлагать X». |

### Ирисочка — приведение к актуальному образу (фитоняшка)

**FACT конфликта:** код = мышка-нутрициолог; docs = эмпатичная советчица; актуальная концепция (промт владельца) = фитоняшка. Промт запрещает считать код каноном.

**REC (без implementation сейчас):** миграция образа аддитивно, в 3 шага, когда дойдёт до Phase 3:
1. **Character Bible** (текстовый канон в проекте: био, речь, ценности, границы) — единый источник для всех промптов; код больше не источник образа.
2. **Замена SYS-промпта** (`SYS_IRISOCHKA`) на фитоняшку: энергичная, спортивная, «движение — часть вкуса жизни», хвалит за активность, предлагает «разминку под блюдо». Тон: подбадривает, не давит. Юмор: про спорт и еду, без бодишейминга. Границы: те же медицинские.
3. **Переезд визуала/присказок**: replace `_QUICK_FACTS` и подписи («🐭 Ирисочка:») на новые; старое содержимое сохранить в git-истории (правило платформы: аддитивно, не удалять).

| Атрибут | Определение (актуальный образ) |
|---|---|
| **Роль** | Движение и уверенность: разминки, лёгкая активность, «как вписать еду в тренировки». |
| **Характер** | Энергичная, тёплая, конкретная; хвалит за попытку, не за результат. |
| **Ценности** | Постоянство важнее интенсивности; еда — топливо и удовольствие. |
| **Отношение к спорту** | «5 минут — уже тренировка», офисная разминка = спорт (совпадает с E2-принципом бэклога). |
| **Отношение к еде** | Без фанатизма: белок — друг, десерт — легально. |
| **Отношение к Пухляшу** | Партнёрство «лень+знания» vs «энергия+движение»; подмигивает его слабостям, страхует его советы. |
| **Отношение к пользователю** | Тренер-подруга: замечает прогресс, предлагает «плюс одно движение». |
| **Стиль речи** | Коротко, живо, с глаголами действия; эмодзи умеренно. |
| **Юмор** | Про отговорки («диван тоже тренировка — если поднимать пульт»), безопасный. |
| **Слабости** | Увлекается и перегибает с активностью — Пухляш её притормаживает. |
| **Границы** | Как у Пухляша: медицинское → дисклеймер; никакого давления при отказе. |

## 6. Character vs Product: три модели

| | **A. Персонаж = интерфейс** | **B. Персонаж = часть продукта** | **C. Персонаж = эмоциональный слой / IP** |
|---|---|---|---|
| Преимущества | дёшево, снимается за неделю, безопасный fallback | дифференциация, retention-механика, использует готовый runtime (FACT) | потенциал бренда/аудитории за пределами nutrition |
| Недостатки | слабое удержание, «ещё один бот» | требует памяти и состояния (Phase 2–3) | дорогой контент, риск «мило, но бесполезно» |
| Риски | персонажа заберут все | если гипотеза H3 ложна — впустую Phase 3 | размывает фокус питания |
| Инвестиции | минимальные | средние (memory + character state) | высокие (контент, арты, события) |
| Проверяемо сейчас | да (косметика) | да — эксперимент §12 | нет (нужна база B) |

- **CURRENT BET: Model B.** Персонажи — часть продукта и носители памяти. Основание: единственная свободная клетка дифференциации (Stage 1 §4: Character=3 только у нас), готовый runtime (FACT), а модель B — единственная, где эксперимент §12 даёт чистый ответ.
- **FALLBACK: Model A.** Если эксперимент §12 покажет D7-дельту < порога (см. §12), персонажи остаются как тон интерфейса (дёшево поддерживать), весь бюджет уходит в utility-петлю (adaptation, fridge, shopping). Model C не рассматривается до доказательства B.

## 7. Memory (персонажная и продуктовая)

**Принцип: без vector DB, без «умной» памяти — только структурированные таблицы + ограниченный срез в промпт.**

| Слой | Что храним | Как | Источник | Не храним |
|---|---|---|---|---|
| **USER FACTS** | имя/цель/вес/возраст/аллергии/режим/регион/timezone | структурированно: `user_profiles` (уже есть) | онбординг/кабинет | email/телефон (колонки существуют — не используем и не заполняем) |
| **FOOD MEMORY** | что любит/не любит/съел/пропустил/понравилось | структурированно: `meal_state` + `reactions` + `deviations` | reminders, реакции | точные граммы/калории съеденного |
| **BEHAVIOR MEMORY** | «часто пропускает завтрак», «не готовит вечером», «любит быстрые» | структурированно: агрегаты за скользящие 14 дней (материализованный JSON в профиле или таблице `user_behavior`) | вычисляется из FOOD MEMORY | постоянные «диагнозы» поведения — только свежие агрегаты |
| **RELATIONSHIP MEMORY** | шутки, обещания, внутренние приколы | текстовая память: `character_memory(tg_id, kind, text, created_at, expires_at)`, ограничение N последних | вручную из диалогов (Phase 3) | всю историю чата |
| **WORLD MEMORY** | события мира персонажей | текстовая, отдельно, Phase 3+ | сценарии | — |

**Что вообще не надо хранить:** полный лог сообщений (privacy+шум), векторные эмбеддинги (до доказанной нужды), сырую LLM-телеметрию дольше 30 дней.

**Правило попадания в промпт:** контекст персонажа = USER FACTS (полностью) + BEHAVIOR (агрегат) + FOOD (последние 7 дней) + RELATIONSHIP (последние 3 записи). Объём ограничен — это защита стоимости и галлюцинаций.

## 8. Product State: canonical source of truth

| Entity | Source of Truth | Lifetime | Кто изменяет |
|---|---|---|---|
| user | `user_profiles` | постоянный | онбординг, кабинет, miniapp(после auth) |
| профиль (поля) | `user_profiles` | постоянный | онбординг/кабинет |
| цель | `user_profiles.goal` | до смены | онбординг |
| активная диета | `diet_programs` (status=active) | до смены/завершения | diet_picker (выбор), adaptation |
| программа (структура+weeks) | `diet_programs` | постоянный (история) | генерация при выборе/адаптации |
| текущая неделя | `weekly_plans` (Diet Program, week_no) | 1 неделя | планировщик недель |
| текущий день | `weekly_plans.days` | 1 день | — |
| meal (плановый приём) | `meal_state` | день | reminder flow |
| статус meal (eaten/skip/replace) | `meal_state.status` | день, потом агрегат | пользователь (кнопки), система (таймаут) |
| рецепт | `recipes` (+связка с meal) | постоянный | Recipe Engine |
| reaction | `reactions` | постоянный | пользователь |
| deviation | `deviations` | постоянный (агрегируемый) | reminder flow |
| character memory | `character_memory` | 90 дней rolling | персонаж-флоу |
| behavior aggregates | `user_behavior` (или JSON в профиле) | пересчёт ежедневно | фоновый job |
| progress/вес | (Phase 5) | — | пользователь |
| **LLM-ответы** | **НЕ source of truth** | — | кэш/лог только |

Правило: **каждая сущность имеет ровно одну таблицу-источник**; всё остальное — производное или лог. Это устраняет сегодняшнее раздвоение (диета-на-экране vs diet_master vs user_profiles).

## 9. Roadmap (Hypothesis → Change → Measurement → Decision)

### PHASE 0 — PRODUCT FOUNDATION (продукт начинает помнить)
**Цель:** состояние пользователя становится постоянным; базовая гигиена.

Состав (пересмотрен относительно промта — убрано лишнее, добавлено критичное):
1. `diet_programs` + сохранение выбора в `diet_picker` (+ кэш недельного плана).
2. `weekly_plans`: план как данные (days/meals), не текст на экране.
3. Canonical profile: единый онбординг (слить 2 воронки), профиль целиком читается генераторами (вес/цель/здоровье/регион → промпты).
4. Reminder ↔ Plan: напоминание говорит, что **по плану**, и пишет статус в `meal_state` (кнопки уже спроектированы — это фундамент Phase 1).
5. Ирисочка: перевод на LLMFactory (долг HIGH из аудита — безопасность+стабильность); Character Bible как канон (текст, без замены образа пока).
6. Security-гигиена: initData-валидация для miniapp-API (или отключение роутов до Mini App), дисклеймер на диет/fitness-контент.
7. Аналитика-минимум: event-log таблица + события §11.

**Не входит:** адаптация, память персонажей, холодильник, Mini App.

### PHASE 1 — CLOSE THE LOOP (пользователь живёт по плану)
**Цель:** plan → reminder → eat/skip/replace → state update работает ежедневно.
- Кнопки реакции в напоминаниях + таймаут-статусы.
- Быстрая замена: 3 варианта в один тап (по профилю; холодильник — позже).
- Мягкая обработка пропуска («ужин полегче?»).
- **Не делать:** калорийный дневник, веса, граммы (принцип §4).

### PHASE 2 — ADAPTATION (система учитывает историю)
**Цель:** следующая неделя отличается **по причине** поведения — наблюдаемо.
- Weekly planner читает: пропуски (время/день), отказы (блюда), реакции (вкусы), время готовки, бюджет.
- Aggregate → промпт адаптации + **visible change**: «Ты дважды отложил гречку — заменила на рис» (Ирисочка объясняет).
- Behavior aggregates (14 дней) как данные.

### PHASE 3 — CHARACTER MEMORY (персонажи помнят — только после реального состояния)
- `character_memory` + ссылки на прошлые события в речи.
- Миграция Ирисочки в фитоняшку (Bible → SYS-промпт → визуал/фразы).
- Примеры полезной памяти (не «я помню макароны»):
  - «В прошлый четверг тоже не успел — вот вариант на 10 минут» (поведение);
  - «Ты просил без лактозы — проверила ужин» (безопасность);
  - «Неделю назад ты выбрал 16/8 и держался 9 дней — продолжаем?» (отношение+прогресс).
- Гонка гипотезы H3 (эксперимент §12) — на этой фазе.

### PHASE 4 — FOOD OPERATING LOOP (холодильник/покупки/бюджет — одно состояние)
- Pantry: что есть дома (ввод ленивый: из замен и покупок).
- Shopping: из плана недели, минус Pantry, с количествами; галочки покупок кормят Pantry.
- Leftovers/бюджет/быстрые решения — приоритезация замен из реального содержимого.

### PHASE 5 — PRODUCT EXPANSION (только при доказанном retention)
- Mini App (если Telegram-UX упирается в потолок — метрики §11), progress/вес, расширение мира персонажей, события, monetization-эксперимент (§13), интеграции.

## 12. Experiment: персонаж (A/B)

**Дизайн:** при наборе ≥60–80 новых пользователей (акция/таргет-посты/взаимопиар в Telegram-нишевых каналах):
- **Group A (50%):** та же функциональность (план, напоминания, замены, адаптация), но сообщения нейтральные: «Обед по плану: …». Без имени, без характера, без шуток. Системное имя бота нейтральное.
- **Group B (50%):** идентично, но interaction layer = Пухляш (+Ирисочка в адаптации/объяснениях). Одинаковый план/рецепты/частота — меняется только слой (FACT-возможность: слой уже отделен в коде — vibes/mood/форматтеры).

Флаг группы пишется в профиль при онбординге; события аналитики общие.

**Измеряем:** D1, D7, D30; reminder response rate; число взаимодействий; **return after missed meal** (главная метрика «заботы»); week completion.

**Пороги решения (заранее зафиксированные):**
- **KEEP CHARACTER:** D7(B) − D7(A) ≥ +10 п.п. **или** response rate +15 п.п. **или** return-after-missed ≥ +20 п.п. → персонаж = часть продукта (Model B), инвестировать в Phase 3-память.
- **REDUCE CHARACTER:** D7(B) ≤ D7(A) и response rate не хуже ±5 п.п. → Model A (тон-элемент), бюджет → utility.
- Серая зона (±): продлить эксперимент на 2 недели, добавить качественные интервью 5–10 пользователям.

Честность: если набор <60 пользователей не идёт — эксперимент откладывается, решение по косвенным метрикам (№9, №10) не принимается как финальное.

## 14. Architectural Consequences (простая архитектура, без микросервисов)

| Решение roadmap | Следствие для текущего кода | Сложность |
|---|---|---|

## 15. Security Gates (минимум, перед каждой фазой)

| Фаза | Обязательный минимум |
|---|---|
| 0 | initData-валидация miniapp-API **или** роуты отключены; секреты только в .env/vault; ключи LLM не в коде; **health/ограничения пользователя — hard rule в каждом LLM-промпте** (аллергии не игнорируются никогда); логи без персонального контента сообщений |
| 1 | дисклеймер на diet/fitness-контент; кнопки не могут изменить чужое состояние (проверка tg_id в callback) |
| 2 | behavior aggregates — только агрегаты, без сырой истории в промптах лишний раз; право пользователя «забудь мои предпочтения» |
| 3 | character memory: лимит хранения (90 дней), без чувствительных данных (здоровье/деньги — только факты в user_profiles, не в памяти персонажа); право «забудь» распространяется на память |
| 4 | pantry/shopping — данные остаются локальными в БД; никакой передачи третьим лицам |
| 5 | до платежей: минималка по данным карт (Telegram Stars — платёж не проходит через нас); privacy-страница |

Не enterprise-compliance: это минимальный безопасный уровень для продукта с health-контентом.

## 20. Final Strategic Recommendation

**CURRENT PRODUCT STRATEGY.** «Пухляш» строится как **планировщик питания, который сам ведёт состояние**: сохранённая диета-программа → недельный план → напоминания с реакцией в один тап → адаптация следующей недели по фактическому поведению, — на дистрибуции Telegram, без подсчётов и без конкуренции с трекерами. Персонажи (Пухляш — планирование и поддержка, Ирисочка-фитоняшка — движение и объяснения) — interaction layer и носители памяти продукта, проверяемые отдельным экспериментом.

**CURRENT BET (одна гипотеза).** *Если система сама помнит контекст, планирует и адаптируется, а персонажи делают взаимодействие человеческим — пользователь возвращается (D7 ≥25%) и живёт по плану (week completion ≥30%) без ведения дневника.*

**FALLBACK.** Если эксперимент §12 → REDUCE CHARACTER: персонажи остаются тоном интерфейса (Model A, дёшево), весь бюджет — в utility (адаптация, pantry/shopping, качество планов); продукт позиционируется чисто как «анти-трекер планировщик» и конкурирует скоростью ценности, а не характером. Если не подтверждается H2 (адаптация): остаётся «план + напоминания + замены» как стабильный utility без остатка.

**BIGGEST RISK.** **Недостаток пользователей для проверки гипотез.** Вся машина метрик/A/B требует порядка 60–100 новых пользователей за месяц; при 2 текущих и нулевом маркетинге даже идеальное исполнение Phase 0–2 не даст статистики. Смягчение: дистрибуция — не «потом», а параллель с Phase 0 (посты в нишевых Telegram-каналах о «боте, который решает что есть», бесплатно) — иначе строим вслепую.

**NEXT 30 DAYS (≤10 действий, последовательность доказательства, не backlog):**
1. **Неделя 1:** `diet_programs` + сохранение выбора + `weekly_plans` (критический путь 1–2).
2. **Неделя 1:** unified onboarding (слить воронки) —canonical profile.
3. **Неделя 1–2:** profile → генераторы (вес/цель/здоровье/регион в промпты) + Ирисочка → LLMFactory.
4. **Неделя 2:** Reminder ↔ Plan: напоминание «по плану» + кнопки съел/заменил/не успел в meal_state (это Phase 1-ядро).
