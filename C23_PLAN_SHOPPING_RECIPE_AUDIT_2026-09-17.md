## 1. WEEKLY PLAN

### Как представлен (FACT)

| Слой | Что есть |
|---|---|
| Генерация | `_get_week_plan()` (`bot_handlers/diet_picker.py`): 1 LLM-вызов (gemini-3.1-flash-lite через LLMFactory, timeout 45s) → JSON `{days:[{day, breakfast/lunch/dinner/snack}], shopping_list, tips}`. Приёмы — объекты `{"название": str, "ккал": int}`. Фоллбэк: `_heuristic_week_plan()` без LLM |
| Persist | `planner.persist_plan_bundle()` (`planner/slots.py`): атомарно `diet_programs` + `weekly_plans` + `meal_state` + `events`. `days`/`shopping_list`/`tips` — JSON-текст в колонках. Календарные границы `start_date`/`end_date=start+6` |
| meal_state | **28 строк на план** = 7 дней × 4 слота (breakfast/lunch/dinner/snack) — materialized только фактические слоты (PATCH-4). `planned_ref={"day_index":i,"meal":slot}`, `planned_text` (текст названия), `status='planned'`, `recipe_id` |
| Структура | Структурированный JSON — **FACT**. Не «простыня»: план разбираем по дням/слотам программно |

### Прод-снимок (FACT, 2026-09-17)
- `diet_programs: 1`, `weekly_plans: 1`, `meal_state: 28` (все `planned`)
- Пример days: `{"day":"Понедельник","breakfast":{"название":"Омлет с овощами…","ккал":400},…}`
- events: `onboarding_started/completed, diet_program_created, plan_created, plan_saved, plan_viewed`

### Можно ли однозначно получить отдельные блюда?
- **Из `days` и `meal_state` — ДА**: каждый слот имеет `planned_text` + позицию (`planned_ref`).
- **Из блюда → рецепт — НЕТ**: `recipe_id = NULL` у всех 28 строк; связи план↔recipes не существует (writer'а нет).

### Критический пробел (FACT)
**Reader'ов `weekly_plans`/`meal_state` в `bot_handlers/`, `modules/`, `api/` — ноль.** План пишется и показывается один раз из FSM-памяти; повторно посмотреть план нельзя; meal_state никогда не читается и не обновляется (контракт `set_meal_status` есть — вызовов нет).

## 4. RECIPES

### Сущность recipe — ЕСТЬ, полноценная (FACT)
`recipes` (80 строк в проде): `title, mode(quick/home/restaurant/pp), description, ingredients JSON, steps JSON, calories_per_serving, protein_g/fat_g/carbs_g, cook_time_minutes, servings, tags JSON, source, created_at, updated_at`. Пример: «Скрэмбл с авокадо и черри», ингредиенты «Яйца куриные - 4 шт.» — количества внутри текста строки.

### Генерация (FACT)
| Поток | Кнопка/handler | Профиль? | Сохранение |
|---|---|---|---|
| По запросу+режиму | «👨‍🍳 Рецепты» FSM (query→mode) | ✅ prompt_builder (cook/budget/experiment/time/excluded) | ✅ `_save()` |
| Случайный по режиму | та же FSM (режим без запроса) | ✅ | ✅ |
| Холодильник | «🧊 Холодильник» (≥2 ингредиента) | ❌ | ✅ |
| По бюджету | «💰 По бюджету» (сумма) | ❌ | ✅ |
| Пухляш | «🍝 Рецепт от Пухляша» (mood/сезон/диета, `build_recipe_context` allowlist PATCH-6) | ✅ | ✅ |
| Scheduler-напоминание приёма | `meal_schedule_v2._fire` → `generate_puhlyash_recipe` | ✅ | **❌ НЕ сохраняется** |

Мелкие факты: `_parse` не проставляет `source` (дефолт 'gemini'); `recipe_sessions` — мёртвая таблица (0, писателей нет).

### «Название блюда» vs «полноценный рецепт» (FACT — ключевая развилка)
- План содержит **только название+ккал**. Ингредиентов/шагов в плане НЕТ.
- Полноценный рецепт генерируется **только по свободному запросу пользователя** и **никак не связан** с блюдом из плана: нет кнопки «рецепт для этого блюда», нет матчинга по названию, `meal_state.recipe_id` всегда NULL.
- 80 рецептов в БД существуют параллельно плану — связь plan→recipe не используется, повторных генераций одинаковых названий система не избегает.

## 9. ВЫВОД

### FACT (главное)
1. План — структурированные данные и **уже материализован** до слотов (meal_state 28 строк) — фундамент продуктового цикла есть.
2. Список покупок = нетипизированные строки от LLM; продукта/количества/единиц как данных нет.
3. Цены/стоимость/бюджет недели — отсутствуют полностью.
4. Рецепты — зрелая изолированная сущность (80 шт., 5 потоков, 1 вызов на рецепт), но **не связаны с планом** (`recipe_id` всегда NULL).
5. `shopping_lists`, `recipe_sessions`, `fridge_sessions`, `diary_entries` — мёртвые таблицы (0 строк, 0 писателей).
6. **Reader'ов плана нет**: пользователь видит план один раз; meal_state не читается и не обновляется — «что съесть сегодня» и отметки отсутствуют.
7. LLM-стоимость цикла уже минимальна: 1 вызов на план; рецепт — 1 вызов, из плана без LLM не выводим.

### UNKNOWN
- Уникальность названий 80 рецептов (возможен скрытый кэш-потенциал) — не проверялось (требует read-only группировки по title; вне объёма).
- Реальная частота запросов рецептов пользователями (реакция 1 шт. на 80 рецептов намекает, что сохранение почти не используется повторно).

### MISSING (для целевого цикла «план→покупки→бюджет→рецепт»)
1. Reader/UX: «показать план», «что сегодня», отметки слотов (контракт `set_meal_status` уже есть в коде).
2. Связь meal↔recipe (заполнение `meal_state.recipe_id` при генерации рецепта для блюда).
3. Структурированный shopping list (items: name/qty/unit/category/source_slots) вместо строк.
4. Вся ценовая подсистема (price source, уровни Россия→регион→город→магазин→персональная) — **только через Product Gate** (см. промпт 7.md §6–9).

### RECOMMENDATION (порядок, без реализации)
1. **Reader-first (дёшево, без LLM):** кнопка «📅 Мой план» → чтение active weekly_plans; «🍳 Сегодня» → meal_state по today; отметки eaten/skipped через существующий `set_meal_status`. Это превращает мёртвые данные в живой цикл.
2. **Recipe-link:** при генерации рецепта из контекста плана — заполнять `meal_state.recipe_id` (схема уже готова).
3. **Shopping list v2:** структура items на стороне генерации (формат промпта — отдельное решение, ADR-2 Phase 0 сознательно фиксирует текущий формат; менять только как задачу с реверси-гейтом).
4. **Цены/бюджет:** не строить до Product Gate; для промпта 7.md этот аудит — фактура §5/§9/§15.
